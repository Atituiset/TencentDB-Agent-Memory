# 记忆模型：L0 → L3 的分层生长

分层是整个记忆体系最重要的结构决策。本章先讲清每层存什么、为什么这样切，再讲层与层之间如何转化。

## 四层的定义

对话首先作为 L0 原样保存，再由异步 Pipeline 提炼为不同粒度的记忆：

| 层级 | 名称 | 保存什么 | 主要用途 |
| :--- | :--- | :--- | :--- |
| **L0** | Conversation | 原始对话与完整上下文 | 核对原话、时间和来源 |
| **L1** | Atom | 从对话提取的事实、偏好、约束与事件 | 精确召回可执行信息 |
| **L2** | Scenario / Profile | 围绕项目或场景组织的知识块（Agent Profile） | 快速恢复一个工作场景 |
| **L3** | Core / Persona | 长期画像、稳定模式与高层认知 | 让 Agent 迅速进入用户和团队语境 |

一个类比：L0 是原始录音，L1 是会议纪要里的逐条要点，L2 是按项目归档的案例卷宗，L3 是对这个人和这支团队的"人物侧写"。

## 为什么必须分层

如果只有一层"记忆库"，会立刻撞上两个矛盾：

**召回精度 vs 上下文效率。** 直接在 L0 上做检索，能找到原话但噪音极大——一段闲聊里可能只有一个关键约束。而 L1 把事实提炼成原子条目后，检索的命中质量完全不同。反过来，如果只存 L1，又会丢失"这句话到底是怎么说的"这类需要回溯原文的场景。

**进入语境的速度 vs 事实的准确。** 每次对话都从 L0 重建认知太慢；只靠 L3 的画像又容易过度概括。实际可用的策略是分层的组合拳：**平时用 L2/L3 快速进入语境，需要具体事实时再通过检索回到 L1/L0。**

生成和召回都遵循这个分层逻辑，且召回结果还会经过条数、字符预算和超时限制——避免记忆反过来占满上下文，喧宾夺主。

## 层间转化：异步提炼管线

L1/L2/L3 不是实时生成的。写入 L0 后，后台 Pipeline 按条件触发：

```text
L0 写入 ──► [Pipeline Scanner] ──► 任务队列 ──► [Pipeline Worker]
                                                    │
                    ┌───────────────────────────────┤
                    ▼                 ▼             ▼
              L1 抽取(原子化)    L2 场景归纳     L3 画像更新
```

触发节奏有几个精心设计的细节：

- **按轮数触发**：默认每积累 N 轮对话（`everyNConversations`，默认 5）跑一次 L1；
- **预热机制**：冷启动阶段阈值按 1 → 2 → 4 → 8 → … 翻倍爬升到 N，保证最初的几轮对话也能尽快产出第一批记忆，而不是让新用户等五轮才看到第一条 L1；
- **空闲触发**：会话闲置超过 `l1IdleTimeoutSeconds` 也会触发，避免"差一轮永远不跑"；
- **层级依赖**：L2/L3 在 L1 的基础上归纳，形成 L0 → L1 → L2/L3 的依赖链。

提炼由 LLM 完成，每一层有固定的输出协议：L1 是 JSON 原子条目，L2 是 Scene Markdown，L3 是 Persona/Doctrine 文档。协议本身不可被自定义 Prompt 修改（只能调整关注点与归纳策略），这保证了下游消费方的稳定性。

## 存储形态

各层的落盘方式并不一致，这是理解源码时的重要背景：

- **L0/L1** 以结构化记录存于 SQLite（或 TCVDB），支持 FTS5 全文 + 向量双路检索；
- **L2/L3** 本体是 Markdown 文件（`profiles/{scope}/scene_blocks/*.md`、`persona.md`），存本地目录或 COS，元数据行在数据库中登记；
- 每次生成都记录溯源引用（用了哪个 Prompt 的哪个版本、输入来自哪些 L0/L1），支持按 Memory ID 反查生成日志。

## 召回时的分层策略

Proxy 和 Adapter 在组装上下文时对四层的用法截然不同，这个对照表在进阶篇会反复出现：

| 层级 | 接入 prompt 的方式 |
| --- | --- |
| L0 | 不注入。通过只读搜索工具供模型主动查询 |
| L1 | 不直接注入。通过工具接口按需召回（保护 KV cache） |
| L2 | Agent Profile，直接注入 system prompt |
| L3 | Team/Global 记忆，直接注入 system prompt |

一句话总结这个设计的动机：**稳定的进缓存，易变的走工具。** L2/L3 变化频率低，注入后可以命中上游的 prompt cache；L0/L1 每轮都在变，一旦内联注入就会击穿缓存，所以暴露成模型可以主动调用的检索工具。
