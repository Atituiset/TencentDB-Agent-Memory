TencentDB Agent Memory 深度指南

它不是聊天记录仓库，也不是普通 RAG

给一个新系统定位，最好的方式之一是说清楚它不是什么。本章把 TencentDB Agent Memory 放在两个常见参照物旁边——聊天历史存档和普通 RAG——通过对比来呈现它的设计取舍。

这张表值得逐行咀嚼，因为每一行背后都是一个具体的设计决策。

RAG 解决"能查到什么"，这里还要解决"谁可以用、哪个版本有效、应该给哪个 Agent"

普通 RAG 系统的核心循环是：切片 → 向量化 → 相似度检索 → 塞进上下文。它回答的问题只有一个："给定查询，语料库里有什么相关的？"

但团队场景的真实问题要复杂得多：

  • 谁可以用？ 一份包含客户事故细节的排障记录，也许该给本团队的 Agent 读，但不该出现在其他部门的上下文里。RAG 的向量库没有"权限"这个维度。
  • 哪个版本有效？ 排障方法会迭代，文档会更新。检索出来的那条 2024 年的 SOP 还是当前的最佳实践吗？
  • 应该给哪个 Agent？ Release Checklist 对 Reviewer 是关键资产，对 Scout 是纯噪音。全局注入既浪费 token 又稀释注意力。

所以本项目把记忆组织为带 Owner、版本、可见性和绑定关系的资产，先做权限收敛（Team / User / Agent / ACL），再做语义召回。"先鉴权、后召回"这个顺序是不可颠倒的。

结构化理解 vs 切片命中

RAG 处理文档的方式是把它们切成片段。这在"找一段相关文字"时够用，但在两类任务上明显不足：

需要结构时。 "这份部署手册的整体流程是什么？""A 方案和 B 方案的取舍依据在哪一节？"——这些问题需要的是文档的骨架和页面间的关系，而不是零散的段落。Wiki 引擎用 LLM 把文档抽取成结构化页面并构建链接图谱，让 Agent 可以像浏览站点一样下钻（详见 MemoryKnowledge 内幕）。

需要语义关联时。 "改了这个函数会影响哪些调用方？"——文本相似度检索对此无能为力，因为"调用"关系不体现在字面上。CodeGraph 直接索引符号与调用边，把 impact analysis 变成一次图查询。

经验 vs 记录

最后是 Skill 与对话记录的区别。一条聊天记录说"我们是这样解决连接池泄漏的"；一个 Skill 则把这个过程提炼为：触发条件是什么、按什么步骤操作、如何验证结果生效、有哪些注意事项和版本。前者是化石，后者是可以被再次执行的程序。

这也是为什么 Skill 子系统有完整的版本管理、资源文件存储和审核流——它的设计目标是被复用，而不只是被查到。

三条技术主线的预告

把上面的差异收拢起来，就是项目在技术实现上反复强调的三个"不是……而是……"：

  1. 记忆不是平铺记录，而是逐层生长 —— L0 到 L3 的分层模型与异步提炼管线；
  2. 记忆不是全局 Prompt，而是 Agent 的 Loadout —— Fixed Binding + ACL 的装配机制；
  3. 知识不整库注入，而是按需调用 —— /v3/tools/list + /v3/tools/call 的工具化协议。

全景篇接下来的章节会把这三条主线逐一落到架构和数据流上。
