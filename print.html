TencentDB Agent Memory 深度指南

Agent 记忆的问题意识

从一个很实际的问题出发

使用 AI Agent 工作一段时间后，几乎每个人都会遇到同样的挫败感：重复劳动。

项目背景讲过了，换个 Session 就得再讲一遍。文档读过了，每个新 Agent 都要从第一页重读。一套排障方法已经跑通了，下次遇到同类问题，Agent 还是会从零摸索。这些成本不是一次性的，而是随着每一次新会话、每一个新 Agent、每一位新成员不断重付。

TencentDB Agent Memory 的出发点，就是对准这个问题：怎样减少使用 Agent 时的重复工作？

答案不是"把聊天记录存下来"。存下来的对话只是化石——它能证明发生过什么，却不能让下一个 Agent 少走弯路。真正有价值的，是从对话中提炼出的那些可复用的经验：

已有信息 → 可复用记忆资产 → 更少 Turns → 更少返工 → 更稳定的结果和更高的效率

所以这个项目对 Memory 的定义比"记住对话"要宽得多：凡是能让下一个 Agent 少走弯路的信息，都应该被保存、组织并复用。

三类最典型的浪费

把"重复工作"拆开看，至少有三类浪费是当前 Agent 工作流的常态：

第一类：关于人和约束的上下文反复丢失。 "别重构旧的鉴权模块，移动端还在用它。"——这类代价很高的上下文，本不该靠人每次口头提醒。用户的偏好、项目的约束、历史上的关键决策，这些信息散落在过去的对话里，却没有一个地方让它们持续生效。

第二类：已经练会的技能无法继承。 一个 Agent 花了四十轮对话才搞明白的上线检查流程、SQL 优化手法、Review 关注点，在会话结束时就蒸发了。下一个 Agent（甚至是同一个 Agent 的下一次会话）只能重新踩坑。

第三类：文档和代码的理解成本每次重付。 Agent 接手任务的第一个动作往往是遍历文件目录、通读文档来建立认知。这份学习成本你已经付过了——付给上一个 Agent 的时候。它应该变成存档，而不是每次重新支付。

记忆的价值在于流动与继承

如果记忆只存在单个 Agent 的私有空间里，它的价值是有上限的。真正放大价值的是团队化：工作中产生资产，资产在团队中流动，新成员进来直接读档。

这正是本项目 Memory Hub 的设计核心——面向 Agent 团队的记忆中枢，让经验完成一个完整的循环：

  1. 自动沉淀资产：从对话和任务中生成 Chat Memory 与 Skill，把文档和代码变成 Wiki 与 CodeGraph，再统一管理、审核和路由。
  2. 可迁移、兼容多 Agent：记忆资产与 Agent 框架解耦，可以跨框架迁移，也可以由团队内的多个 Agent、多个成员共享和维护。
  3. 冷启动友好：导入已有文档、代码库和历史对话 Session，新的 Agent 团队从现有经验开始工作，不必从头学起。

Benchmark 的佐证

这套理念有一个可量化的检验：在 PersonaMem 基准上（它专门检验 Agent 能否在长期交互后正确理解和运用用户信息），不启用本项目时得分 48%，启用后达到 76%，相对提升 +59%。

数字本身不是重点；重点是它验证了一个朴素的判断——当记忆被结构化地沉淀并按需召回时，Agent 对"人"和"事"的理解会发生质变，而不是量变。

TencentDB Agent Memory 是什么

一句话定位

TencentDB Agent Memory 是一套开源的 Agent 记忆基础设施：它把 Agent 工作中产生的对话、技能、文档理解与代码理解，沉淀为四类可管理的记忆资产，并通过一个团队化的 Hub 让这些资产在人、Agent 与框架之间流动、复用与继承。项目由腾讯 TencentDB 团队发起，MIT 协议开源，全部服务基于 Node.js（>= 22.16）构建。

四个"大脑器官"

项目的功能版图可以概括为四个互相配合的子系统，每个对应一种记忆资产：

Chat Memory：能记住人和事的大脑

Chat Memory 保留用户的偏好、事实、决策和交互历史，并按 L0 → L3 四层逐级提炼（详见记忆模型）。每个 Agent 创建时自动获得一份独立记忆，下次对话不必从自我介绍开始。

它的设计动机很直接："别重构旧鉴权模块，移动端还在用。"——这种代价高昂的上下文，不应该依赖人每次提醒，也不应该随着会话关闭而消失。

Skill 库：会积累经验的肌肉记忆

Agent 做完复杂工作后，系统可以从对话和工具调用中提炼出可复用的 Skill——排障流程、Review 要点、上线检查清单。需要时再注入到指定 Agent 的上下文中。

这里的 Skill 不只是一段 Prompt：它有版本、资源文件、触发边界、执行步骤和验证规则。个人 Skill 默认私有；经过审核后可分享给团队，再装配给其他 Agent。"练会一次，全队可用"是它的目标。

Wiki + CodeGraph：同时看懂文档和代码的知识地图

  • Wiki 把产品文档、设计方案和运维手册交给 LLM 抽取为结构化页面，并自动生成页面间的链接图谱（这一思路源自 Andrej Karpathy 的 "LLM Wiki" 构想）。Agent 不必先读完所有文件目录再开工，而是可以搜索、沿链接下钻。
  • CodeGraph 对代码库建立索引：符号、文件、调用关系和影响路径。Agent 不仅能查到"代码在哪"，还能在动手改代码之前先做 impact analysis——"改了这里可能影响哪"。

两者平时都只是可调用的工具，只有真正需要时才进入上下文，避免整库注入撑爆窗口。

Memory Hub 面板：由人掌握的操作台

Memory Hub 不是一块展示数据的展板，而是一个操作台：在这里建 Team、录成员、创建 Agent，审核、分享并配装记忆资产，统一管理 Owner、版本、状态、可见性与使用次数。人始终握有最终控制权——分享是一个明确的动作，而不是默认的泄漏。

系统形态：三件套 + 一组接入件

从部署视角看，项目由三个核心服务组成（通常用 Docker 一键拉起）：

服务默认端口职责
Memory Core8420记忆存储与处理、元数据管理、Skill 数据面

围绕这三个服务，项目提供两类接入方式：

  1. Proxy 接入（零代码）：把 Claude Code、CodeBuddy、Codex、WorkBuddy、DeepSeek Harness、Hermes、OpenClaw 等 Agent 的 API base URL 指向 Proxy 即可。协议不变、代码不改，不需要插件、Hook 或 MCP Server。
  2. SDK / Adapter 接入（深度定制）：TypeScript 与 Python SDK 直接对接 Memory Core Gateway；OpenClaw 插件与 Hermes 插件则示范了自研 Adapter 的标准姿势。

一个具象的玩法：一个人的公司

README 里有一个广为流传的例子，值得在这里重述，因为它浓缩了整套产品的使用哲学——给一个人的公司组一支会成长的 Agent 队伍：

Tiny but Serious Inc.
├── 👤 You · 定目标 / 做判断
├── 🔭 Scout · 查资料 / 找机会
├── 🛠 Builder · 写代码 / 做产品
├── 🧪 Reviewer · 测试 / 挑毛病
└── 🧠 Agent Memory · 让经验留在队伍里

这不是开四个彼此失联的聊天窗口，而是在组一支角色不同、能够继承团队经验的 Agent 小队。招人之后还要配装备——每个角色拿到不同的 Loadout：

🔭 Scout
   ├── 用户访谈 Chat Memory
   ├── 市场研究 Wiki
   └── 竞品分析 Skill

🛠 Builder
   ├── 产品 Wiki
   ├── 项目 CodeGraph
   └── Feature Delivery Skill

🧪 Reviewer
   ├── 历史事故 Chat Memory
   ├── 项目 CodeGraph
   └── Release Checklist Skill

不同角色、不同装配：少给噪音，多给它完成工作真正需要的记忆。公司可以很小，经验可以一直复利。

技术实现要解决的三个问题

项目在技术上的自我约束可以概括为一句话：不追求"存下所有东西"，而是解决三个问题——什么值得留下、谁可以使用、下一次怎样少拿但拿对。这三个问题分别对应本书全景篇将要展开的三条技术主线：

  1. 记忆不是平铺记录，而是逐层生长（L0–L3 分层 + 异步提炼管线）；
  2. 记忆不是全局 Prompt，而是 Agent 的 Loadout（Fixed Binding + ACL 决定每个 Agent 能带走哪些资产）；
  3. 知识不整库注入，而是按需调用（Wiki/CodeGraph 以 tools 协议按需读取）。

后续章节将逐条展开这些机制的实现细节。

核心概念：资产、Team 与 Loadout

在深入架构之前，先建立一套贯穿全书的词汇表。这套概念体系是理解所有后续设计的前提——几乎每一个 API、每一张表、每一段注入逻辑，都围绕它们展开。

记忆资产（Memory Asset）

Chat Memory、Skill、Wiki 和 CodeGraph 在系统内被统一登记为记忆资产。资产是权限、版本与路由的基本单位，每个资产都携带这些属性：

  • Owner：资产的归属用户，自动获得该资产的管理权；
  • Team：资产归属的团队容器；
  • 可见性：private / team / restricted / agent（详见资产体系）；
  • 版本与状态：Skill 有显式版本链；Wiki/CodeGraph 有构建状态机；
  • 使用记录：最近是否被使用、被哪些 Agent 绑定。

点开一条资产时，面板关心的不只是"它写了什么"，还有"它从哪来、是哪个版本、分给了谁、最近是否被使用"。这是它与一个"聊天记录仓库"最本质的区别。

组织三元组：Team / Agent / Task

Coding Agent 使用记忆必须落到具体的三元组上：

Team（团队） 是一组资产的归属容器。memory、skill、knowledge 都归 Team 所有，成员关系决定了谁能读写哪些资产。

Agent（智能体） 是 Team 内的角色化执行者。创建时要填写清晰的 description 和 system prompt（角色说明），例如"bug-fix 工程师""前端评审 agent""SQL 优化师"。注意一个容易混淆的点：在这个体系里，Agent 是被管理的元数据实体和调用方——MemoryCore 不负责托管、调度或运行 Agent 本身。

Task（任务） 是"这一次工作的抓手"，比如"修复登录页 XSS""上线 v1.4 灰度"。Task 是可选的：不建 Task 也能用，但 L2/L3 记忆会缺 Task 维度；对话中产生的记忆会关联到当前 Task 上，成为日后回溯的线索。

三元组加上 User 一起构成了 v3 数据面的强隔离维度：几乎所有 /v3/* 接口都要求 team_id、agent_id、user_id 三元组（通过请求体或 x-tdai-* Header 传入），可选的 session_id 进一步限定会话范围。

Loadout：Agent 的记忆装配

传统做法是把一大段"全局记忆"塞进 system prompt，所有人共享、所有会话都背。本项目的做法完全不同：每个 Agent 通过 Fixed Binding + ACL 决定它能带走哪些资产。

运行时的决策顺序是：先按 Team、User、Agent 和可见性缩小权限范围，再按当前问题做语义召回。于是：

  • 团队可以共享经验，却不必共享全部隐私；
  • 换 Agent 或换框架，只需重新装配，不必重新训练；
  • 不同角色拿到不同的装配——Scout 不需要 Release Checklist，Reviewer 不需要市场研究 Wiki。

"配装备"这个比喻值得记住：Memory Hub 里给 Agent 绑定资产的页面，本质上就是在编辑它的 Loadout。

Memory Instance 与 spaceId

Memory Instance（记忆实例） 是 Memory Core 中一组数据的逻辑隔离单元。每个请求都必须通过 x-tdai-service-id Header 声明自己属于哪个实例；本地部署通常固定叫 default。在 Proxy 的 URL 路径里，实例 ID 以 <spaceId> 的形式出现：

http://127.0.0.1:8096/claude-code/default
                            └─ agent-source ─┘└spaceId┘

多租户部署时，不同实例的数据、配置乃至 Pipeline 状态彼此独立。

会话初始化（Session Init）

当一个 coding agent 第一次经过 Proxy 对话时，Proxy 会拦截请求并引导完成一次会话绑定：依次选择本次会话所属的 Team → Agent → Task（可选）。绑定完成后：

  • 后续每一轮请求自动注入所选 Agent 的 L2/L3 记忆、Skill 与 Knowledge；
  • 原始对话（L0）自动回流到 MemoryCore；
  • 同一进程内的后续轮次不再重复询问。

对 Claude Code 这类交互式客户端，选择以原生问答工具的形式弹出；对无法响应交互表单的平台，则通过 x-team-id / x-agent-id / x-task-id 请求头直接注册。

数据面与管理面

最后一条分界线是 数据面 与 管理面 的分离：

  • 数据面处理记忆内容本身：写入 L0、检索 L1/L2/L3、Skill 的增删改查与抽取。它要求完整的三元组隔离。
  • 管理面处理元信息：User、Team、Agent、Task、Asset 及其权限关系（/v3/meta/*），以及知识资产的登记（/v3/knowledge/*）、自定义 Prompt（/v3/memory-prompt/*）等。

Panel 是管理面的主要消费者；Proxy 和各 Adapter 主要工作在数据面上。理解这条线，后面阅读 API 列表和源码目录时会顺畅很多。

它不是聊天记录仓库，也不是普通 RAG

给一个新系统定位，最好的方式之一是说清楚它不是什么。本章把 TencentDB Agent Memory 放在两个常见参照物旁边——聊天历史存档和普通 RAG——通过对比来呈现它的设计取舍。

这张表值得逐行咀嚼，因为每一行背后都是一个具体的设计决策。

RAG 解决"能查到什么"，这里还要解决"谁可以用、哪个版本有效、应该给哪个 Agent"

普通 RAG 系统的核心循环是：切片 → 向量化 → 相似度检索 → 塞进上下文。它回答的问题只有一个："给定查询，语料库里有什么相关的？"

但团队场景的真实问题要复杂得多：

  • 谁可以用？ 一份包含客户事故细节的排障记录，也许该给本团队的 Agent 读，但不该出现在其他部门的上下文里。RAG 的向量库没有"权限"这个维度。
  • 哪个版本有效？ 排障方法会迭代，文档会更新。检索出来的那条 2024 年的 SOP 还是当前的最佳实践吗？
  • 应该给哪个 Agent？ Release Checklist 对 Reviewer 是关键资产，对 Scout 是纯噪音。全局注入既浪费 token 又稀释注意力。

所以本项目把记忆组织为带 Owner、版本、可见性和绑定关系的资产，先做权限收敛（Team / User / Agent / ACL），再做语义召回。"先鉴权、后召回"这个顺序是不可颠倒的。

结构化理解 vs 切片命中

RAG 处理文档的方式是把它们切成片段。这在"找一段相关文字"时够用，但在两类任务上明显不足：

需要结构时。 "这份部署手册的整体流程是什么？""A 方案和 B 方案的取舍依据在哪一节？"——这些问题需要的是文档的骨架和页面间的关系，而不是零散的段落。Wiki 引擎用 LLM 把文档抽取成结构化页面并构建链接图谱，让 Agent 可以像浏览站点一样下钻（详见 MemoryKnowledge 内幕）。

需要语义关联时。 "改了这个函数会影响哪些调用方？"——文本相似度检索对此无能为力，因为"调用"关系不体现在字面上。CodeGraph 直接索引符号与调用边，把 impact analysis 变成一次图查询。

经验 vs 记录

最后是 Skill 与对话记录的区别。一条聊天记录说"我们是这样解决连接池泄漏的"；一个 Skill 则把这个过程提炼为：触发条件是什么、按什么步骤操作、如何验证结果生效、有哪些注意事项和版本。前者是化石，后者是可以被再次执行的程序。

这也是为什么 Skill 子系统有完整的版本管理、资源文件存储和审核流——它的设计目标是被复用，而不只是被查到。

三条技术主线的预告

把上面的差异收拢起来，就是项目在技术实现上反复强调的三个"不是……而是……"：

  1. 记忆不是平铺记录，而是逐层生长 —— L0 到 L3 的分层模型与异步提炼管线；
  2. 记忆不是全局 Prompt，而是 Agent 的 Loadout —— Fixed Binding + ACL 的装配机制；
  3. 知识不整库注入，而是按需调用 —— /v3/tools/list + /v3/tools/call 的工具化协议。

全景篇接下来的章节会把这三条主线逐一落到架构和数据流上。

  • MemoryProxy（:8096） 是 Agent 与上游 LLM 之间的透明代理。它在请求转发的前后"顺手"完成会话初始化、记忆注入、对话回流、鉴权与用量上报。对客户端和上游模型来说它都是不可见的——协议原样转发。
  • MemoryCore（:8420） 是记忆与元数据核心。所有 Memory / Skill / Knowledge 元信息的读写最终都落在它身上。Proxy 自己不落任何记忆数据——这是一条重要的分工边界：Proxy 管"接入与转发"，Core 管"存储与处理"。
  • Memory Panel（:8125 生产 / :8123 开发） 是无状态的 Web 管理控制台。它不保存登录会话、不维护本地用户库，只做凭证校验与请求转发聚合。
  • Knowledge Service（:8424 生产 / :8421 开发） 是 Wiki 与 CodeGraph 引擎，负责知识内容的解析、索引和检索。

┌─────────────────────────────────────────────────────────┐
│ 接入层   Proxy（零代码注入）· OpenClaw/Hermes 插件 · SDK    │
├─────────────────────────────────────────────────────────┤

这个分层里最值得注意的设计是管理面与数据面共用同一个 Gateway 进程（都在 :8420 上），但走不同的路由前缀（/v3/meta/* vs /v3/conversation|atomic|skill/*），并且使用不同强度的身份凭证（管理面要求 x-tdai-user-key 用户级密钥，数据面主要靠 Bearer API Key + 三元组隔离参数）。这让单机部署极简，又不妨碍未来拆分。

存储视图

默认形态下（standalone 模式），整个系统的持久化需求出乎意料地轻：

  • SQLite 一个文件搞定元数据、L0-L3 记录、Skill 索引（FTS5 全文 + sqlite-vec 向量）；
  • 本地文件目录（默认 ~/.memory-tencentdb/memory-tdai）存放 Pipeline 产物（persona.md、scene_blocks）、Skill 资源文件和大对象；
  • 除调用 LLM API 外没有必需的外部服务——不需要 Redis、不需要向量数据库就能完整跑通。

同时，每个环节都预留了升级通道：向量检索可切换到腾讯云 VectorDB（TCVDB）获得服务端原生混合检索；大对象可 offload 到 COS；多节点部署时 Proxy 状态可切换到 Redis 或 COS 后端。这种"单机开箱即用、按需逐级放大"的姿态贯穿全部组件。

关键设计不变量

阅读源码之前，先记住几条贯穿全项目的工程决策，它们解释了大量看似奇怪的代码结构：

双部署形态对称。 deployMode: standalone | service 是第一分叉。standalone 下一切状态在进程内（内存队列、setTimeout 定时器、checkpoint 文件）；service 模式下状态外置（Redis Stream 任务队列、分片 ZSET 定时器、分布式锁）。两种模式共享同一套业务 handler。

全链路降级而非崩溃。 sqlite-vec 加载失败 → 降级为纯 BM25；jieba 缺失 → 正则切词；Embedding 未配置 → 只用关键词召回。几乎每个依赖都有 fallback，故障被记录为日志标签而不是异常中断。

幂等与可追溯。 写入按 record_id upsert；Skill 更新用乐观锁；每次 L1/L2/L3 生成都会落一条 Generation Log（记录 Prompt ID、版本、内容哈希），形成完整的证据链。

缓存友好的上下文分层。 召回结果刻意拆成两类：跨轮稳定的内容追加到 system prompt 尾部（命中 prompt cache），每轮变化的内容前置到 user prompt（不污染缓存）。这是 Proxy 注入管线和 Core 召回接口共同遵守的约定。

组件巡礼：Core、Knowledge、Panel、Proxy

MemoryCore：记忆与元数据核心

MemoryCore 统一存储并提供三类数据能力：

  • Memory：L0 对话、L1 原子记忆、L2 场景记忆和 L3 核心画像的存储、生成与召回；
  • Knowledge 元信息：Wiki、CodeGraph 等知识源的标识、类型、状态与关联关系（注意：只存元信息，不存内容——内容解析在 Knowledge Service）；
  • 资产管理元信息：User、Team、Agent、Task、Skill、Knowledge Asset 及成员、归属、访问关系。

它以 Standalone Runtime 形态开源，默认监听 127.0.0.1:8420，使用 SQLite 与本地文件，进程内维护 Pipeline 状态。源码的主要版图：

MemoryCore/src/
├── core/        L0–L3 记忆域模型、Skill 子系统、Prompt 模板、hooks
├── gateway/     HTTP Gateway、v2/v3 路由、各业务 handler
├── services/    Pipeline Scanner / Worker / 调度
├── metadata/    v3 管理面路由与服务（权限校验）
├── store/       SQLite / TCVDB 存储抽象、BM25、Embedding
├── utils/       Pipeline Manager（standalone/service 双形态）
├── openclaw-plugin/   OpenClaw 轻量 Adapter
└── hermes-plugin/     Hermes Memory Provider

对外 API 以 /v3/* 为推荐面（v2 兼容保留）。所有业务调用都必须携带 x-tdai-service-id 声明实例。

MemoryKnowledge：知识引擎

Knowledge Service 是用户侧 Wiki + Code-Graph 引擎，基于 Hono 构建，API 前缀 /v3。它的四块核心能力：

能力说明

Code-Graphgit clone 仓库 → CodeGraph 索引（符号、调用、文件树）→ 探索查询

Tools 协议POST /v3/tools/list、/v3/tools/call，供 Agent 自发现调用

一个容易忽略但关键的机制是 llm_binding：生产链路中 Wiki 生成所用的 LLM 由 Panel 按 x-tdai-service-id 推送绑定（走 Proxy 计费），而不是 KS 自己配置——这样 Wiki 生成的成本可以归账到具体实例。ingest/sync 完成后，KS 会回调 Panel 写回远端元数据。

MemoryPanel：团队记忆控制台

Team Memory Control 是无状态的管理控制台：不保存服务端登录会话、不维护本地用户库，业务数据全部由外部服务持久化。这个定位决定了它的架构——一个精致的"转发 + 聚合"层：

  • kernel 层采用端口-适配器模式（六边形架构）：MetaKernelPort、SkillKernelPort、KnowledgeClientPort 等接口定义了对内核的全部依赖，fetch 实现负责组装凭证头、日志脱敏与超时映射；
  • 实例注册表 metadata-instances.json 描述了 Panel 可连接的所有 Memory 实例（ID、Gateway 地址、API Key），真实文件不入库；
  • 公开 API 统一挂在 /api/v1 下，对元数据操作做白名单代理（55 条 action），对 Chat Memory 等复杂场景提供聚合路由（消除前端 N+1 请求）；
  • 前端是 React 18 + Zustand 的 SPA：工作台任务看板、Wiki 工坊、CodeGraph 工坊、Skill 库、Chat Memory 三视图、成员管理与 Agent 编辑。

安全上 Panel 有几条铁律：用户凭证 user_key 只经 Header 传递；注册表中的 api_key 仅服务端使用绝不下发浏览器；提交前跑 secret-scan.sh。

MemoryProxy：透明 LLM 代理

Proxy 是整个体系里"魔法"最集中的地方——也是设计上最克制的地方。克制在于：它对协议零修改，OpenAI /v1/chat/completions 和 Anthropic /v1/messages 原样转发；魔法在于转发前后的一进一出里完成了八件事：

POST /proxy/<spaceId>/v1/chat/completions | /v1/messages
   ├─ 1. auth ─────── 校验 x-tdai-user-key，解析出 user_id
   ├─ 2. systemUser ─ 命中内部账号则短路透传
   ├─ 3. sessionInit ─ 首次对话弹表单：team → agent → task
   ├─ 4. injection ── system prompt 注入 skill / knowledge / memory
   ├─ 5. rateLimit ── spaceId × 最终模型 TPM/QPM 限流
   ├─ 6. forward ──── 转发到上游 LLM
   ├─ 7. extract ──── 一轮结束后异步回流 conversation + L0
   └─ 8. report ───── ClickHouse / Langfuse / Opik / Credit 上报

支撑这些动作的子系统包括：五后端的统一存储抽象（cos/sqlite/fs/memory + redis）、按 agent name 覆盖上游的路由表、mem: 会话指令拦截、以及可选的一致性哈希负载均衡网关。进阶篇有专章拆解。

SDK（TypeScript / Python）覆盖 v3 数据面与管理面的全部端点：

  • MemoryClient：L0-L3 读写与检索，构造时强制三元组隔离；
  • SkillClient：Skill 全生命周期 + 对话增量摄取；
  • MetadataClient：约 60 个管理面方法；

Python 版同时提供同步与异步客户端（httpx）。

记忆模型：L0 → L3 的分层生长

分层是整个记忆体系最重要的结构决策。本章先讲清每层存什么、为什么这样切，再讲层与层之间如何转化。

四层的定义

对话首先作为 L0 原样保存，再由异步 Pipeline 提炼为不同粒度的记忆：

层级名称保存什么主要用途
L0Conversation原始对话与完整上下文核对原话、时间和来源
L1Atom从对话提取的事实、偏好、约束与事件精确召回可执行信息
L2Scenario / Profile围绕项目或场景组织的知识块（Agent Profile）快速恢复一个工作场景
L3Core / Persona长期画像、稳定模式与高层认知让 Agent 迅速进入用户和团队语境

一个类比：L0 是原始录音，L1 是会议纪要里的逐条要点，L2 是按项目归档的案例卷宗，L3 是对这个人和这支团队的"人物侧写"。

为什么必须分层

如果只有一层"记忆库"，会立刻撞上两个矛盾：

召回精度 vs 上下文效率。 直接在 L0 上做检索，能找到原话但噪音极大——一段闲聊里可能只有一个关键约束。而 L1 把事实提炼成原子条目后，检索的命中质量完全不同。反过来，如果只存 L1，又会丢失"这句话到底是怎么说的"这类需要回溯原文的场景。

进入语境的速度 vs 事实的准确。 每次对话都从 L0 重建认知太慢；只靠 L3 的画像又容易过度概括。实际可用的策略是分层的组合拳：平时用 L2/L3 快速进入语境，需要具体事实时再通过检索回到 L1/L0。

生成和召回都遵循这个分层逻辑，且召回结果还会经过条数、字符预算和超时限制——避免记忆反过来占满上下文，喧宾夺主。

层间转化：异步提炼管线

L1/L2/L3 不是实时生成的。写入 L0 后，后台 Pipeline 按条件触发：

L0 写入 ──► [Pipeline Scanner] ──► 任务队列 ──► [Pipeline Worker]
                                                    │
                    ┌───────────────────────────────┤
                    ▼                 ▼             ▼
              L1 抽取(原子化)    L2 场景归纳     L3 画像更新

触发节奏有几个精心设计的细节：

  • 按轮数触发：默认每积累 N 轮对话（everyNConversations，默认 5）跑一次 L1；
  • 预热机制：冷启动阶段阈值按 1 → 2 → 4 → 8 → … 翻倍爬升到 N，保证最初的几轮对话也能尽快产出第一批记忆，而不是让新用户等五轮才看到第一条 L1；
  • 空闲触发：会话闲置超过 l1IdleTimeoutSeconds 也会触发，避免"差一轮永远不跑"；
  • 层级依赖：L2/L3 在 L1 的基础上归纳，形成 L0 → L1 → L2/L3 的依赖链。

提炼由 LLM 完成，每一层有固定的输出协议：L1 是 JSON 原子条目，L2 是 Scene Markdown，L3 是 Persona/Doctrine 文档。协议本身不可被自定义 Prompt 修改（只能调整关注点与归纳策略），这保证了下游消费方的稳定性。

存储形态

各层的落盘方式并不一致，这是理解源码时的重要背景：

  • L0/L1 以结构化记录存于 SQLite（或 TCVDB），支持 FTS5 全文 + 向量双路检索；
  • L2/L3 本体是 Markdown 文件（profiles/{scope}/scene_blocks/*.md、persona.md），存本地目录或 COS，元数据行在数据库中登记；
  • 每次生成都记录溯源引用（用了哪个 Prompt 的哪个版本、输入来自哪些 L0/L1），支持按 Memory ID 反查生成日志。

召回时的分层策略

Proxy 和 Adapter 在组装上下文时对四层的用法截然不同，这个对照表在进阶篇会反复出现：

层级接入 prompt 的方式
L0不注入。通过只读搜索工具供模型主动查询
L1不直接注入。通过工具接口按需召回（保护 KV cache）
L2Agent Profile，直接注入 system prompt
L3Team/Global 记忆，直接注入 system prompt

一句话总结这个设计的动机：稳定的进缓存，易变的走工具。 L2/L3 变化频率低，注入后可以命中上游的 prompt cache；L0/L1 每轮都在变，一旦内联注入就会击穿缓存，所以暴露成模型可以主动调用的检索工具。

资产体系与权限模型

如果说分层记忆模型解决的是"什么值得留下"，那么资产体系解决的是剩下两个问题：谁可以使用、如何装配到正确的 Agent。

一切皆资产

四类内容——Chat Memory、Skill、Wiki（llm_wiki）、CodeGraph（code_graph）——在管理面被统一登记为 Asset。每个资产记录：

  • asset_id / asset_type
  • owner（归属用户，自动拥有管理权）
  • team_id（归属团队）
  • visibility（可见性）
  • 版本、状态与使用统计

统一建模的好处是权限逻辑只写一遍：无论是一段 Chat Memory 还是一个 CodeGraph，"谁能读、谁能管、能绑给谁"走的是同一套校验。

四级可见性

可见性语义
private只有 Owner 可读，团队管理员也不例外
team团队成员可读，Owner/Admin 负责管理
restricted通过 User / Role / Agent ACL 精确授权
agent用于同团队 Agent 的定向装配

这套分级的设计哲学是：新记忆和 Skill 默认私有，分享是一个明确动作，不是默认泄漏。 你可以把"发布 Skill"配给 Release Agent，把"架构 Wiki"配给所有开发 Agent，把 CodeGraph 同时给 Coder 和 Reviewer——每一步授权都显式发生。

角色的两层结构

权限主体分两层，混为一谈会出很多"灵异问题"：

全局层：System Admin。 由用户记录的 user_type === 'system_admin' 标识，与是否加入任何 Team 无关。职责是管理用户与团队（建团队、录入成员）。v2.0.0 起 admin 也可使用 Wiki、CodeGraph、Skill 等资产管理功能。

Team 内层：Admin 与 Member。 team.members 表中每个成员带 admin | member | reviewer 角色，负责团队内的资产协作与权限控制。

判定顺序有一条铁律：先判全局角色，再查 team 成员表。资产操作权上还有一个刻意的收敛——admin 不再拥有全局资源特权，只能操作自己 owner 的资产；team admin 可管理本 team 资产。"运维口"（admin 管人）与"应用口"（业务用户管资产）的分离是官方推荐的使用姿势。

Fixed Binding + ACL：Loadout 的实现

Agent 的记忆装配由两个机制配合完成：

Fixed Binding（固定绑定） 是一张 agent ↔ asset 关联表，每条绑定记录 { asset_id, asset_type, injection_mode, priority, created_by }。Chat Memory / Wiki / CodeGraph 走这条路：

  • Wiki/CodeGraph 绑定用 injection_mode='tool'——运行时渲染为 <knowledge_tools> 工具说明块，Agent 按需调用而非全量注入；
  • Chat Memory 借入用 'summary' 模式；
  • 绑定接口是全量覆盖式 set（没有增量端点），所以上层都是"list → append/remove → set"的组合；
  • 每个 Agent 自动拥有一条 id 形如 chat_memory-{team_id}-{agent_id} 的自有记忆资产，默认 private 且固定绑定不可解绑。

ACL（访问控制表） 处理 restricted 场景的精确授权：acl/grant {user_id, asset_id, action: read|write|use}，读门控统一走 acl/check。Owner-only 语义由内核保证。

一个反直觉但合理的设计：Skill 不走 binding，而是 fork 副本。 因为运行时的 <available_skills> 注入和面板的"固定资产"视图都按 owner_agent_id 过滤，仅改 ACL 对这两处无效；所以把 Skill 配给某个 Agent 的唯一机制，是复制一份 owner=目标 Agent 的副本（唯一约束 (team_id, owner_agent_id, name)）。理解了这一点，就理解了为什么面板上的 Skill 操作是"Fork 到 Agent"而不是"绑定"。

切私密不清理绑定的取舍

还有一个体现工程判断的细节：当资产从 team 改回 private 时，系统不会级联清理已有的 Agent 绑定（"脏绑定"）。原因是在内核权限模型下，caller 只能操作自己 owner 的 agent，跨 owner 清理会 403；而保留脏绑定是无害的——下游注入、memory-bridge 和详情页在读取侧都会按当前可见性过滤（apply_visibility_filter=true）。把一致性检查从写入侧挪到读取侧，换来了操作的原子性和简单性。

面板上的落点

这些概念在 Memory Hub 里对应的具体操作：

  • 组队：建立 Team，加入人和 Agent，确定共享边界；
  • 资产背包：打开、搜索、审核和管理四类资产；
  • Agent Loadout 编辑：在 Agent 编辑弹窗里为它增删 Wiki/CodeGraph/Chat Memory 绑定、查看 Skill fork 情况；
  • 权限切换：在 private/team/restricted 之间调整可见性，必要时通过 ACL 收回共享。

一次请求的完整旅程

架构图是静态的，系统真正的性格体现在数据流动上。本章跟随一次典型的 Claude Code 会话，看数据如何在四个服务之间穿行——先看"去程"（请求如何被增强），再看"回程"（对话如何变成记忆），最后看旁路的异步管线。

去程：一次被增强的 LLM 调用

假设你已经在面板上建好了 Team、Agent 和 Task，并按 ANTHROPIC_BASE_URL=http://127.0.0.1:8096/claude-code/default 启动了 Claude Code。当你发出第一句话：

① 鉴权。 Proxy 收到 POST /claude-code/default/v1/messages，取出 x-tdai-user-key（即你的 sk-mem-...），调用 MemoryCore 的 POST /v3/meta/auth/verify 反查出 user_id。此后全链路以这个用户身份行事。

② 会话初始化（仅首次）。 Proxy 发现这是新会话，把请求暂存，向 Claude Code 返回一个 AskUserQuestion 工具调用——在终端里呈现为三连问：选 Team → 选 Agent → 选 Task（可跳过）。选择结果与 session 绑定后持久化；同一进程内的后续轮次不再询问。

③ 注入。 确定绑定后，注入管线开始组装 system prompt 的附加内容：

<tdai_profile_memory>   ← Agent 的 L2 场景块 + L3 画像（读自 Core）
<cloud_skills>          ← 与当前问题相关的 Skill 摘要（RAG 检索）
<skill_tools>           ← 如何通过工具读写 Skill 的说明
<knowledge_tools>       ← 该 Agent 绑定的 Wiki/CodeGraph 两步自发现协议
<session_context>       ← 本次会话绑定的 agent/task 信息

L0/L1 刻意不在其中——它们以 <tdai_memory_tools> 只读工具的形式存在，让模型在需要时主动查询，避免每轮变化的检索结果击穿上游 KV cache。

④ 限流与转发。 按 spaceId × 最终模型 做 60 秒滑动窗口限流后，请求原样转发到 .env 里配置的上游 LLM。

回程：对话变成记忆

上游返回后，Proxy 在响应流结束的瞬间触发两个异步动作：

Skill 归档回流：本轮对话切片被发送到 MemoryCore 的 /v3/skill/conversation/add——进入 Skill 抽取的对话缓冲区，供后台判断"这是否包含一条值得沉淀的可复用方法"。

L0 写入：完整对话写入 MemoryCore 的 L0 存储。到此为止，用户的等待时间几乎没有增加——所有重活都在后台。

旁路：异步提炼管线

MemoryCore 内部，Pipeline Scanner 注意到某会话的新增轮数达到阈值（默认 5 轮，冷启动预热期更快），把任务投给 Pipeline Worker：

  1. L1 抽取：LLM 读对话片段，产出原子记忆条目（事实/偏好/约束/事件），并与已有条目做去重合并；
  2. L2 归纳：满足条件时，相关 L1 被归纳为场景块（Scene Markdown），挂到对应 Agent 的 Profile 下；
  3. L3 更新：跨场景的稳定模式最终汇入长期画像（Persona）。

每次生成都会写一条 Generation Log（用了哪个 Prompt、什么版本、输入输出引用），面板里可以按 Memory ID 精确溯源。

与此同时，如果这轮对话触发了 Skill 抽取判定，一条新 Skill 进入待审状态——它有版本号、资源文件和验证规则，等你在面板上审核后分享给团队。

知识资产的旁路循环

Wiki 和 CodeGraph 有自己独立的生命周期。你在面板上传一批文档或登记一个 Git 仓库后：

Panel ──► Knowledge Service ──► 异步构建（LLM 抽取 / clone+索引）
   ▲                               │
   └──── status-callback ──────────┘
         （ready/failed + 进度事件 + 自动摘要）

构建完成后 Panel 写回资产元数据，资产即可被绑定到 Agent。之后文档更新可以重新 ingest，代码仓库可由 Auto-Sync 定期拉取重建。

观察这个循环

跑通之后，有三个地方能直观看到这套循环在工作：

  • 面板 Chat Memory 页：L0 对话被切分的场景逐步出现；
  • Agent 详情 → Profile：L2 scene 与 L3 persona 在累积；
  • curl http://localhost:8420/health | jq .services.pipelineWorker：tasksConsumed/tasksCompleted 随对话增长。

这就是 README 里那句话的含义："没有 Memory，Loop 可能只是更快地重复。能继承记忆，每一轮才有机会比上一轮更好。"——整个系统的本质，就是把这条循环自动化。

快速开始总览

本部分的目标是让你在半小时内从零跑到"看到记忆在面板里生长"。四章按真实使用顺序排列：

  1. 一键部署三件套 —— 用官方脚本拉起 Memory Core + Memory Hub + Proxy，拿到管理员密钥。
  2. 建立组织结构并接入 Claude Code —— 登录面板建 Team/Agent/Task，把 coding agent 挂到 Proxy 上，完成第一次会话绑定，观察记忆生长。
  3. 更多客户端接入 —— CodeBuddy、Codex、DeepSeek Harness、Hermes、OpenClaw 及任意 OpenAI 兼容平台的接入配置与差异对照。
  4. 冷启动：先读档再开工 —— 把已有的代码库、文档和历史对话导入为资产，让新 Agent 团队从现有经验开始。

部署前的准备清单

开始之前确认这几件事：

  • Docker 已安装且可用（一键部署基于 Docker Compose 式的容器编排）；
  • 两组 LLM 凭证：
    • MEMORY_LLM_*（base URL / API key / model）：供 Memory Core 的记忆提炼和 Wiki 生成内部使用，任何 OpenAI 兼容端点均可；
    • PROXY_UPSTREAM_*：Proxy 转发用户对话请求的上游模型——这决定你在 Claude Code 里实际对话用的模型；
  • 端口 8420 / 8125 / 8424 / 8096 未被占用；
  • 如果打算让局域网内其他机器访问，准备一个可路由的主机地址。

一个常见的取舍问题：两组 LLM 可以配同一个模型。记忆提炼的任务偏轻量（抽取、归纳），给它配一个便宜快速的模型是合理的省钱姿势；PROXY_UPSTREAM_* 则按你的编码质量要求选。

脚本背后发生了什么

理解脚本的编排逻辑，出问题时才知道去哪看。start-all.sh 在 tdai-memory-stack 这个 Docker 网络上按依赖顺序拉起三个容器，每一步都等待健康检查通过再继续：

Memory Core 容器：脚本动态生成一份 standalone 模式的 Gateway 配置（开启 Skill、pipeline 每 5 轮触发、召回阈值 0.3），挂载到容器内并挂一个 named volume 做数据持久化。接着是 init-admin 流程——用 openssl 生成 sk-mem-<32位随机> 作为管理员密钥，调用 /v3/internal/meta/user/init-admin 注册 admin 用户；密钥以严格文件权限落盘为 ./.admin-key，重复执行会复用已有文件。

Memory Hub 容器：合并镜像同时跑 Panel 与 Knowledge Service。它通过容器网络别名 http://memory-core:8420 连接 Core，脚本还会探测宿主机局域网 IP 以生成正确的对外访问地址。

Proxy 容器：同样由脚本从 .env 生成最小 config.yaml，打开三大开关——鉴权（auth）、会话初始化（sessionInit）、记忆接入（tdai）——即 PROXY_FULL_STACK=1 的完整流水线。

全部就绪后，脚本打印服务地址表和一段可直接复制运行的 Claude Code 启动命令。

verify.sh 都检查什么

建议第一次部署前跑一次干跑。它会依次验证：Docker 可用性、.env 存在且必填字段没有遗留 REPLACE_ME 占位、本地镜像是否存在（仅警告）、端口占用情况（仅警告）、以及真实的 LLM 通路预检——对 openai 协议端点发 GET /models（零 token 消耗），对 anthropic 协议端点发一条 max_tokens=1 的探测消息（≤10 token）。两组 LLM 配置相同时自动去重。任何 error 会中止，warning 放行。

这个预检能提前暴露最常见的部署事故：API key 写错、base URL 尾部多了或少了 /v1、模型名不存在、公司网络出口被墙。

注意 KNOWLEDGE_PUBLIC_BASE_URL 必须带 /v3 后缀且 Agent 可达；REMOTE_INSTANCE_* 指向你的 Core 地址。

停止与清理

./stop-all.sh            # 停容器，保留 volume 数据 & admin key
./stop-all.sh --purge    # 连 volume、admin key、proxy config 一起清

数据都在 named volume 里，普通 stop/start 不丢；只有 --purge 才是彻底重来。admin 密钥丢了又没 purge 的话，只能 purge 重建。

建立组织结构并接入 Claude Code

服务起来只是第一步。要让 coding agent 真正用上团队记忆，需要在面板里建组织结构，然后在会话里绑定它们。本章走完这条最核心的路径。

第 1 步：登录管理面板

打开 http://localhost:8125，用 start-all.sh 结尾打印的 admin user_key（即 deploy/global-images/.admin-key 里的 sk-mem-...）登录。

这里推荐养成一个好习惯——隔离运维口与应用口：

  • admin 是"运维口"，用来管人（建团队、录成员）；
  • 业务用户是"应用口"，用来管资产、跑 agent。

具体操作：在「用户管理」新建一个 normal 用户（面板操作或直接调 API 均可）：

ADMIN_KEY=$(cat ./.admin-key)
curl -sS -X POST http://localhost:8420/v3/meta/user/create \
  -H "x-tdai-user-key: $ADMIN_KEY" \
  -H "x-tdai-service-id: default" \
  -H "Content-Type: application/json" \
  -d '{"username":"you"}' | jq

返回体里的 data.default_user_key 是新用户的登录密钥——只在创建时返回这一次，立即保存。之后退出 admin，用这把新 key 重新登录。

第 2 步：建 Team / Agent / Task

Coding Agent 使用记忆必须落到 team / agent / task 三元组上：

  1. Team：左侧「团队」→ 新建。它是资产的归属容器。
  2. Agent：进入 Team → 「Agent」→ 新建。给它填一段清晰的角色说明（description + system prompt），例如"bug-fix 工程师""前端评审 agent"。
  3. Task（可选）：Team →「任务」→ 新建，比如"修复登录页 XSS"。记忆会关联到 Task；不建也能用，但 L2/L3 会缺 Task 维度。

至少建 1 个 Team + 1 个 Agent 再继续。

v2.0.1 起有冷启动优化：新建团队自带默认 Agent 并预置导入 Skill，不必从零开始配。

第 3 步：把 Claude Code 指向 Proxy

export ANTHROPIC_BASE_URL=http://127.0.0.1:8096/claude-code/default
export ANTHROPIC_AUTH_TOKEN="<业务用户的 sk-mem-...>"
claude --model <PROXY_UPSTREAM_MODEL 配的模型>

三个值的含义值得逐个理解：

  • ANTHROPIC_BASE_URL 把 CC 的 API 从 anthropic.com 改指本机 proxy；路径里的 default 是 memory 实例 ID；
  • ANTHROPIC_AUTH_TOKEN 是业务用户的 user_key——proxy 用它去 Core 反查身份，只有这个用户拥有的 team/agent/task 会出现在下一步的选择表单里；
  • --model 必须是 .env 里 PROXY_UPSTREAM_MODEL 配置过的上游模型名。

第 4 步：首次会话的三连问

每开一个新的 CC 会话，proxy 会借 CC 自带的 AskUserQuestion 工具依次弹出：

1. 请选择本次会话所属的 Team：
   ○ Team A    ○ Team B
2. 请选择「Team A」下要使用的 Agent：
   ○ bug-fix 工程师    ○ 前端评审 agent
3. 请选择关联的任务（可选）：
   ○ 修复登录页 XSS    ○ [跳过任务关联]

箭头键选择、回车确认。选完之后 proxy 记住本次会话的绑定，后续每一轮自动注入所选 Agent 的 L2/L3 记忆、skill 与 knowledge；同一进程内不再重复询问。想换绑定的 Team/Agent？开一个新 CC 会话即可重新弹表单。

第 5 步：观察记忆一层层长出来

真实工作几轮之后（改文件、跑测试、给出结论——而不是闲聊），回到面板验证循环是否转起来了：

  • 左侧**「记忆」→ Chat Memory**：L0 原始对话被切分出的 scene 开始出现；
  • Agent 详情页 → Profile：L2 场景块与 L3 画像逐步累积；
  • Skill 列表：如果 LLM 判定对话里有可复用的操作方法，会自动抽出候选 Skill。

命令行侧可以用健康检查看后台管线是否在工作：

curl -s http://localhost:8420/health | jq .services.pipelineWorker
# tasksConsumed / tasksCompleted 应随对话增长

给记忆喂点什么

第一次看到空面板很正常——记忆需要素材。几个立竿见影的做法：

  • 和 agent 做真实工作对话：让它读代码、改文件、复现一个 bug；
  • 明确说出约束和偏好："这个项目不要引入新依赖""我们统一用 pnpm"——这些会被提炼为 L1 原子记忆；
  • 完成一次复杂排障后输入 mem:create-skill，把过程归档为 Skill；
  • 直接导入历史对话 Session（见冷启动）。

{

      "id": "claude-sonnet-4-20250514",

      "vendor": "claude",
      "apiKey": "<业务用户的 sk-mem-...>",

注意两点：id 必须与 Proxy 上游支持的模型匹配；apiKey 用业务用户的 user_key。CodeBuddy 4.10.2–4.10.4 有已知 Bug（不携带 sessionId 导致 session init 失败），请用 ≥ 4.10.5 或 ≤ 4.10.1。

Codex CLI

编辑 ~/.codex/config.toml：

model_provider = "team-proxy"
model = "claude-opus-4.7"
disable_response_storage = true

[model_providers.team-proxy]
name       = "TDAI team-proxy"
wire_api   = "responses"
base_url   = "http://127.0.0.1:8096/codex/default"
experimental_bearer_token = "<业务用户的 sk-mem-...>"

两个关键细节：wire_api = "responses" 必填（Codex 走 Responses 协议）；disable_response_storage = true 关闭本地缓存，否则第二轮起可能命中缓存跳过注入。

首次对话前必须切到 Plan 模式（Shift+Tab）：默认 Agent 模式会自动执行 proxy 返回的 session-init 表单工具、跳过用户选择，导致永远绑不上 Team/Agent/Task。选完三元组后再切回 Agent 模式正常使用。

DeepSeek Harness (dsh)

编辑 ~/.dsh/settings.yaml：

llm-deepseek:
  apiKeyEnv: PROXY_USER_KEY
  baseURL: http://127.0.0.1:8096/dsh/default   # 尾巴不要加 /v1！
  reasoningEffort: high

密钥放 ~/.dsh/.credentials.yaml 的 PROXY_USER_KEY: 字段，并收紧权限（dsh 启动时强制检查）：

chmod 700 ~/.dsh && chmod 600 ~/.dsh/.credentials.yaml

Web UI 里每个新对话首帧会渲染 4 步按钮式选择器（是否关联团队资产 → Team → Agent → Task）；CLI headless 模式 proxy 会自动检测无交互能力而 bypass session-init，直接透传。

Hermes 与 OpenClaw：header 直注册模式

这两个框架无法响应交互式表单，因此通过请求头直接完成 session 注册，跳过弹窗：

# Hermes ~/.hermes/config.yaml（节选）
base_url: http://<proxy-host>:<port>/hermes/default
api_key: <user_key>
extra_headers:
  x-team-id: <team_id>
  x-agent-id: <agent_id>
  x-task-id: <task_id>          # 当前版本必填
  x-conversation-id: <自定义会话标识>

OpenClaw 在 ~/.openclaw/openclaw.json 的 models.providers 里做等价配置（baseUrl 用 /openclaw/<spaceId>，headers 同上）。

两条当前版本的已知限制要心里有数：

  1. x-task-id 必填——缺了它 proxy 会尝试弹表单，而这俩框架接不住，最终 session bypass（注入与回流全部失效）。切换任务需要手动改配置。
  2. x-conversation-id 静态指定——同一 ID 的所有请求共享同一 session；每次开新对话需手动更换 ID，否则沿用上次会话状态。

官方已在路线图中计划让 task 可选并优化 conversation ID 体验。

其他平台（通用接入法）

http://<proxy-host>:8096/<agent-source>/<spaceId>
  • <agent-source> 从 claude-code / codebuddy / workbuddy / codex / hermes / openclaw 中选用（其他平台可伪装成其中之一）；
  • 必带 Header：Authorization: Bearer <user_key> + 四个 x-* header（同上表）；
  • 缺 header 的平台将触发 session bypass——透传正常，但记忆不生效。

接入后的通用验证清单

无论哪个客户端，接入后建议按顺序确认三件事：

  1. 首条消息触发 session init（或 header 注册成功），面板上能看到会话绑定；
  2. 对话几轮后，Core /health 的 pipelineWorker 计数增长；
  3. 输入 mem:help 能返回指令帮助——说明注入管线工作正常。

冷启动：先读档，再开工

多数 Agent 接手新任务的第一件事，是重新学习你的项目——遍历目录、通读文档、摸索规范。这些学习成本你早就付过了。TencentDB Agent Memory 把它们变成存档：代码库、文档、历史对话三类已有资产都可以导入，让新 Agent 团队直接从现有经验开始。

三条导入通道

你有什么导入后变成处理方

导入代码库 → CodeGraph

在 CodeGraph 工坊登记一个仓库地址，KS 会 git clone 并构建索引。构建完成后：

  • Agent 可以搜索代码、查 callers/callees、在改代码前做 impact analysis；
  • 把它绑定给 Builder/Reviewer 角色的 Agent（Loadout 编辑），运行时以 <knowledge_tools> 工具形式按需调用；
  • 开启 Auto-Sync 后可定时拉取 git 更新自动重建。

上传文档或文件后，LLM 会把它们抽取为结构化页面并自动生成页面间的引用图谱。价值在于两点：Agent 不必先读完所有文件再开工，可以搜索和沿链接下钻；文档之间的关系（"A 方案被 B 方案取代"这类链接）被显式保存下来。

导入对话 → Skill 与 Chat Memory

把过去与 Agent 的对话 Session 从面板导入，系统会走与实时回流相同的管线：写入 L0、后台提炼 L1-L3、判定是否包含可抽取的 Skill。这是把"老 agent 的经验"迁移给"新 agent 队伍"最直接的路径。

用 Loadout 完成装配

资产就绪后，最后一步是把它们配给正确的 Agent。打开 Agent 编辑弹窗：

  • Wiki / CodeGraph / Chat Memory 走 allocate/unbind 增量绑定；
  • Skill 通过 fork 复制到目标 Agent 名下；
  • 每个角色只配它需要的——少给噪音，多给完成工作真正需要的记忆。

一个务实的冷启动剧本

假设你要为一支三人的 Agent 小队（Scout/Builder/Reviewer）冷启动：

  1. 登记产品 Wiki（产品文档 + 设计方案），等 ready；
  2. 登记主仓库 CodeGraph，等 ready；
  3. 导入过去一个月的关键排障对话 Session；
  4. 面板审核自动抽出的 Skill 候选，通过后 fork 给对应角色；
  5. 给 Scout 配市场 Wiki，给 Builder 配 CodeGraph + 产品 Wiki，给 Reviewer 配 CodeGraph + 事故 Chat Memory；
  6. 各自开一次会话验证 <knowledge_tools> / <available_skills> 注入正常（mem:help 有响应即说明链路通）。

完成后，这支队伍的第一轮对话就已经"读过你的项目"了——不再重新训练每一个 Agent，给它读档。

常见问题排查

本页收录一键部署路径上最高频的问题。按"症状 → 原因 → 解法"组织。

会话初始化类

CC 会话没有弹选择表单？

PROXY_ENABLE_SESSION_INIT=1 没开。start-all.sh 默认已打开；如果你手动改过 .env 或用 PROXY_FULL_STACK=0 起的，重启 proxy：PROXY_FULL_STACK=1 ./start-proxy.sh。

表单选择项空空的，或只有别人的 team？

确认当前账号在面板里建过 Team 和 Agent。Proxy 只列出当前 user_key 对应用户 own 的资产——用 admin key 但没建过资产、或用了别人的业务用户，都会看到空列表。

Codex 永远选不了 Team/Agent/Task？

首次对话前没切 Plan 模式。默认 Agent 模式会自动执行 session-init 表单的工具调用、跳过用户选择。先 Shift+Tab 切 Plan 再发第一条消息。

服务健康类

面板显示 "Panel API 8125 未启动"？

docker ps 看 tdai-memory-hub 是否 healthy；不 healthy 就 docker logs tdai-memory-hub 找报错——大概率是 REMOTE_INSTANCE_URL / LLM_BASE_URL 之类配错。

本地起 Proxy 一直刷 ECONNREFUSED 127.0.0.1:6379？

示例配置默认启用 Redis，而本机没跑 Redis。纯本地开发改为 redis.enabled: false + storage.enabled: true（backend: sqlite），状态走本地 SQLite。

Core 起不来，提示需要 API Key？

非回环地址监听时必须设置 TDAI_GATEWAY_API_KEY。另外注意一键部署脚本有个已知约定：MEMORY_CORE_GATEWAY_API_KEY 需留空——proxy 的 auth 校验调用 verify 时不带 Bearer 头，强开 Gateway 层鉴权会不兼容。

记忆生成类

L1/L2 一直没跑起来，面板没有记忆产出？

最常见的两个原因：

  • 配置了 promptMode=code 但对话内容是闲聊——LLM 判定无可沉淀内容返回 0 条。改回 chat 或做真实工作对话（改文件、跑测试、给结论）。
  • 对话轮数还没到触发阈值。默认每 5 轮触发一次（有预热机制，前几轮更快）；会话闲置超时也会触发。可用 /health 的 pipelineWorker 计数确认管线是否消费了任务。

想切换到别的 team/agent？

新开一个 agent 会话（新窗口/新 session）就会重新弹绑定表单。

导入的历史会话时间线错乱？

v2.0.1-beta.1 已修复该问题，请升级到最新镜像。

客户端兼容类

CodeBuddy 不弹 session init？

版本 4.10.2–4.10.4 存在已知 Bug：请求不携带 sessionId。换 ≥ 4.10.5 或 ≤ 4.10.1。

Hermes/OpenClaw 记忆完全不生效？

按顺序检查四个 header 是否齐全且值正确：x-team-id / x-agent-id / x-task-id / x-conversation-id。缺任何一个都会 session bypass。特别注意 x-task-id 当前必填，以及静态 conversation ID 需要"每次新对话手动更换"。

dsh 报错 baseURL 相关异常？

检查两点：尾巴不能带 /v1（dsh 客户端硬编码 ${baseURL}/chat/completions）；.credentials.yaml 权限必须是 600、目录 700。

数据与迁移类

从旧版升级后数据不见了/启动报格式错误？

v1.x/v0.x（数据格式 v2）升级到 v2.0.0+（v3）必须先跑迁移脚本再启动新版 Gateway：

python scripts/migrate-v2-to-v3/v2-to-v3-migrate.py ~/.memory-tencentdb/memory-tdai --dry-run
# 确认无误后去掉 --dry-run 执行

迁移前务必备份整个数据目录。详见进阶篇升级与数据迁移。

其他注意事项

  • Wiki 与 CodeGraph 是异步构建的，导入后需等待处理完成才能 ready；
  • 全自动记忆路由仍在迭代，当前通过面板人工绑定资产即可覆盖绝大多数场景；
  • 遇到本文未覆盖的问题，到 GitHub Issues 提交，项目方承诺 24 小时内响应。

贯穿全篇的四条设计主线

MemoryCore 内幕：存储与网关

MemoryCore 是全系统的数据权威。本章从存储抽象讲到 Gateway 鉴权，覆盖阅读其源码所需的全部背景。

存储抽象：一套接口，两种后端

src/core/store/ 下有一层存储工厂（factory.ts），按配置把记忆读写路由到不同实现：

  • SQLite 路径（默认，standalone）：单文件数据库。元数据与记录在常规表中；检索靠 FTS5（全文，配合 jieba 中文分词；jieba 缺失时退化为正则切词）+ sqlite-vec（向量余弦相似度）。sqlite-vec 加载失败时整个向量路降级为 no-op，只剩关键词召回。
  • TCVDB 路径（腾讯云向量数据库）：面向规模化部署。集合命名带实例前缀（如 {db}_profiles、{db}_skills）；最大优势是服务端原生混合检索——dense + sparse + RRFRerank 在一次 API 调用内完成（tcvdb.ts:1027 附近可见 rerank: { method: "rrf", k: 60 }），省去客户端融合。

Embedding 是可选项：未配置 OpenAI-compatible Embedding API 时，系统纯 BM25 运行；配置后自动启用双路。

管理面的元数据存储同样有双后端：SQLite 的 meta_users / _user_keys / _teams / _team_members / _agents / _tasks / _task_agents / _participation_logs / _assets / _agent_fixed_assets / _asset_acl / _config_params 系列表，或 MongoDB（store/sqlite-adapter.ts vs mongodb-adapter.ts，按 {prefix}_{instance_id} 隔离）。

大对象（L2/L3 Markdown 产物、Skill 资源文件、生成日志）走文件系统或 COS offload，数据库里只登记元数据行。

三层鉴权

Gateway（src/gateway/server.ts，Node 原生 http 服务，:8420）的请求要过三道身份检查，各自回答不同的问题：

Authorization: Bearer <apiKey>        ← 第一层：调用方是否被允许访问这个 Gateway
x-tdai-service-id: <instance>         ← 第二层：操作哪个 Memory 实例（数据隔离）
x-tdai-user-key: <sk-mem-...>         ← 第三层（管理面）：代表哪个用户行事

第一层的 Bearer Key 由 TDAI_GATEWAY_API_KEY 配置；本地回环监听且未设置时可省略。第二层是强制的——所有业务请求都必须声明实例。第三层用于 /v3/meta/* 管理面，Gateway 会校验 user_key 并以解析出的用户身份做 owner/ACL 权威判定。

幂等与可追溯的实现纪律

翻源码时会反复遇到这几条纪律：

  • upsert 写入：所有记录按 record_id 幂等写入，重复提交不产生脏数据；
  • 乐观锁：Skill 更新携带 expected_version，并发修改冲突直接报错而不是静默覆盖；
  • 只追加审计：对记忆的修改写 memory_audit 表，不覆盖历史；
  • JSONL append 带 ETag/位置校验：对象存储上的追加写会先验证当前内容指纹。

这些纪律共同保证了一个性质：任何一条记忆的当前状态，都可以沿着 Generation Log 与 Audit 记录还原出完整的来龙去脉。

配置系统

Gateway 配置按优先级加载：TDAI_GATEWAY_CONFIG 指定的 YAML/JSON → 当前目录 → 数据目录 → 环境变量 → 内置默认值。YAML 支持 ${VAR} 形式引用环境变量。常用模板三份：

  • tdai-gateway.standalone.yaml：最小单机 Memory 配置；
  • tdai-gateway.yaml：Standalone + Skill 默认配置；
  • tdai-gateway.proxy.yaml：经 OpenAI-compatible Proxy 调用模型。

关键配置段（src/config.ts）：pipeline.everyNConversations（默认 5）、recall.scoreThreshold（默认 0.3）、llm.*（模型三件套）、skill.*（Skill 模块开关）。完整环境变量清单见附录环境变量速查。

生成管线与召回机制

记忆系统有两个引擎：一个负责"长出来"（生成管线），一个负责"找回来"（召回）。本章深入两者的实现。

生成管线：从 L0 到 L3

调度结构

L0 写入 ──► Timer Scanner ──► 任务队列 ──► Worker Permit Pool ──► Pipeline Worker
   (services/timer-scanner.ts)              (worker-permit-pool.ts)   (pipeline-worker.ts)
  • Scanner 周期扫描各会话的未处理轮数，判断是否达到触发条件；
  • 队列在 standalone 模式是进程内 Map（checkpoint 到文件防重启丢失），service 模式是 Redis Stream；
  • Permit Pool 控制并发度，service 模式下配合分布式锁保证同一会话的任务不被多节点重复消费。

触发条件与预热

触发由两个条件任一满足：

  1. 会话新增轮数 ≥ 阈值。稳态阈值即 pipeline.everyNConversations（默认 5）；
  2. 会话空闲超过 l1IdleTimeoutSeconds——避免"差一轮永远不跑"的尴尬。

预热机制（pipeline-manager.ts 的 warm-up 逻辑）值得单独一提：新会话的阈值不是直接从 5 开始，而是 1 → 2 → 4 → 8 → … → N 翻倍爬升。效果是新用户的第 1 轮对话结束后就能看到第一条 L1 记忆，而不是对着空面板怀疑人生；随着交互加深，触发频率逐渐放缓到稳态，避免碎片化提炼。

各层的提炼实现

每层有专属的 Prompt 模板与后处理（src/core/prompts/）：

  • L1 抽取（l1-extraction.ts + l1-dedup.ts）：LLM 从对话片段提取原子条目（事实/偏好/约束/事件），输出 JSON 协议；随后与既有 L1 做去重合并——语义等价的旧条目被更新而非重复创建。
  • L2 场景（scene-extraction.ts）：把相关 L1 归纳为 Scene Markdown 块，写入 profiles/{scope}/scene_blocks/*.md，数据库登记元数据（TCVDB 路径下 ID 为 profile:v1:{sha256}）。
  • L3 画像（persona-generation.ts）：跨场景沉淀稳定模式为 Persona 文档 persona.md。

固定输出协议（L1 的 JSON 结构、L2/L3 的 Markdown 格式）不可被自定义 Prompt 篡改——自定义只能调整"关注什么"，不能改变"输出成什么样"。这是下游消费方（注入器、面板渲染）赖以工作的契约。

每次生成的完整溯源（Prompt ID、版本、内容哈希、输入输出引用）写入 Generation Log，见专章。

召回机制：少拿但拿对

混合检索的三种模式

召回入口在 src/core/hooks/auto-recall.ts 与 src/core/tools/memory-search.ts / conversation-search.ts：

  • keyword：FTS5 BM25 全文检索；
  • embedding：向量相似度；
  • hybrid（默认）：双路并行检索，结果用 RRF（Reciprocal Rank Fusion） 融合。

RRF 的实现非常克制（RRF_K = 60，取自原始论文的标准常数）：

score(item) = Σ 1 / (k + rank_i + 1)

某条记录同时出现在关键词榜和向量榜时，两边的 RRF 分数累加——天然奖励"两种信号都认为相关"的结果。SQLite 路径下融合在客户端完成（先超额检索再合并）；TCVDB 路径则直接用服务端原生 hybridSearch 短路返回。

召回质量的护栏

原始相似度之外还有多层过滤：

  • 分数阈值：recall.scoreThreshold（默认 0.3）以下的结果丢弃；
  • 条数上限：限制返回条目数；
  • 字符预算：格式化后的总长度受限，防止记忆占满上下文；
  • 超时：召回整体有超时控制，慢查询宁可返回空也不阻塞主链路。

错误也是分级的：Embedding 未配置这类情况以结构化 RecallError（code 20001 等）返回，调用方可感知地降级，而不是抛异常。

缓存友好的上下文拆分

auto-recall 里有一处明确注释的性能设计（H-15 系列），值得所有做 LLM 应用的人学习。召回结果被拆进两个通道：

  • appendSystemContext：persona、场景导航、工具使用指南——这些内容跨轮稳定，追加到 system prompt 尾部，可以命中上游 provider 的 prompt cache；
  • prependContext：本轮查询命中的 L1 相关记忆——每轮变化，前置到 user prompt，不污染缓存前缀。

顺序很重要：稳定的在前、易变的在后（对 system prompt 而言），才能让缓存前缀尽量长。Proxy 的注入管线遵循同一哲学（见 Proxy 内幕）。

Skill 子系统速写

Skill 是数据面里最复杂的业务对象，几个要点：

  • 存储：SQLite 路径用 vectors.db 的 skills / skill_fts / skill_vec 三表（BM25 + 向量）；资源文件按 <skill_id>/v<version>/files/ 组织；TCVDB 路径用 {db}_skills 集合；
  • 版本化：skill-versioning.ts 维护版本链，更新走 expected_version 乐观锁；
  • 抽取：对话经 /v3/skill/conversation/add 进入缓冲区（COS 上按 {space}/{user}/{team}/{agent}/{session}/ 组织），后台判定是否值得归档；另有 fast-path 处理显式触发的 mem:create-skill；
  • 降级：向量路不可用时检索自动回退 BM25 并记录 SkillDegradation 事件，契约层面保证 mode 不被静默吞掉；
  • 隔离：CI 对这个模块有一条硬性红线——禁止引入直接 fs import、禁止触碰 pipeline-worker/integrations/redis（见升级与迁移章的 CI 一节）。

自定义 Prompt 与生成溯源

自动抽取的记忆不可能永远符合你的团队语境。MemoryCore 提供了两个配套机制：自定义 Memory Prompt（调整提炼的关注点）与 Generation Log（追溯每条记忆是怎么来的）。两者合起来，把记忆从"系统产出的黑盒"变成"可调校、可审计的资产"。

自定义 Prompt 的能力边界

先说清它能改什么、不能改什么：

  • ✅ 调整 L1/L2/L3 提炼时的关注点与归纳策略，例如"重点提取架构决策、兼容性约束、风险和可复用方法"；
  • ❌ 不能修改固定输出协议——L1 的 JSON 结构、L2 Scene Markdown 和 L3 Persona/Doctrine 的格式是硬契约。

配额限制：每个 Memory Instance 最多 500 个自定义 Prompt；单个 Prompt 内容最长 10,000 个 Unicode 字符。

绑定模型与优先级

Prompt 本体和目标绑定分开存储。绑定目标有三层，解析时按优先级生效：

Agent > Team > Instance > 系统内置
  • Agent 由 team_id + agent_id 唯一确定；
  • 未命中任何自定义 Prompt 时完全使用系统默认；
  • 命中时只追加客户的记忆策略（不是替换系统 Prompt）；
  • 删除 Prompt 会清理相关绑定，运行时自动回退到下一级。

版本语义：更新保持 memory_prompt_id 不变并执行 version += 1，已有绑定的新生成任务自动使用最新版本——正在跑的旧任务不受影响。

主要接口

POST /v3/memory-prompt/create     # 创建
GET  /v3/memory-prompt/get       # 查询
POST /v3/memory-prompt/update    # 更新（version+1）
POST /v3/memory-prompt/delete    # 删除（清理绑定）
POST /v3/memory-prompt/set       # 绑定到 Agent/Team/Instance
GET  /v3/memory-prompt/log       # 设置操作日志
GET  /v3/memory-generation-log/list | /get   # 生成溯源

创建示例：

curl -sS -X POST http://127.0.0.1:8420/v3/memory-prompt/create \
  -H "Authorization: Bearer ${TDAI_GATEWAY_API_KEY}" \
  -H "x-tdai-service-id: local-memory" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "architecture-decisions",
    "layer": "l1",
    "prompt": "重点提取架构决策、兼容性约束、风险和可复用方法。"
  }'

本地未配置 TDAI_GATEWAY_API_KEY 且只监听回环地址时可省略 Authorization；x-tdai-service-id 始终必填。

Generation Log：证据链设计

每次 L1/L2/L3 生成都会落一条溯源记录，回答三个问题：

  1. 用了哪个 Prompt？ 记录 memory_prompt_id、版本、来源（自定义/内置）以及内容的 SHA-256 哈希——注意不保存 Prompt 正文快照，既省空间又避免正文里的敏感信息扩散。
  2. 输入是什么？ 本次生成引用了哪些 L0/L1 记录。
  3. 输出了什么？ 生成的 Memory ID 与结果的存储位置。

实现上分两层：数据库表 memory_generation_refs 做反向索引（"这条记忆由哪个 prompt 版本生成"），完整日志对象写 COS 或本地目录，对象键形如：

memory-generation-logs/v1/layer={l}/date={d}/hour={h}/{倒序ts}__mid={anchor}__lid={logId}.json

倒序时间戳的设计让按时间"新到旧列举"变成一次字典序扫描。按 Memory ID 查询：

curl -sS -G http://127.0.0.1:8420/v3/memory-generation-log/get \
  -H "Authorization: Bearer ${TDAI_GATEWAY_API_KEY}" \
  -H "x-tdai-service-id: local-memory" \
  --data-urlencode "memory_id=<memory-id>" \
  --data-urlencode "layer=l1"

实操建议

一个经过验证的调校流程：

  1. 先观察默认 Prompt 的产出：面板里看 L1 条目是否抓对了重点；
  2. 针对系统性偏差写自定义 Prompt——比如发现它总是忽略性能约束，就加一句"特别关注性能相关约束与权衡"；
  3. 绑定到 Team 层（而非逐 Agent 配置），让整个团队共享同一套提炼口径；
  4. 用 /v3/memory-generation-log/get 对比调校前后同一对话的产出差异；
  5. E2E 验证可跑 npm run e2e:memory-prompt:vdb-cos——它会验证 Agent/Team/Instance 三层 Prompt 的实际模型请求、持久化与 COS 日志，并用唯一测试 ID 清理数据。

SDK 侧：TypeScript 导出 MemoryPromptClient 与 MemoryGenerationLogClient，Python SDK 提供同步/异步双版本，方法一一对应。

MemoryProxy 内幕：注入管线与会话初始化

Proxy 是四个组件里对延迟最敏感的——它卡在每一次 LLM 调用的关键路径上。因此它的所有设计都围绕两个目标：注入要快且不破坏缓存，故障要不阻断转发。

请求处理八阶段

一次带 spaceId 的主模型调用经过：

POST /proxy/<spaceId>/v1/chat/completions | /v1/messages
   ├─ 1. auth ─────── 校验 x-tdai-user-key，解析出 user_id
   ├─ 2. systemUser ─ 命中内部账号则短路透传
   ├─ 3. sessionInit ─ 首次对话弹表单：team → agent → task
   ├─ 4. injection ── system prompt 注入 skill / knowledge / memory
   ├─ 5. rateLimit ── spaceId × 最终模型 TPM/QPM 限流
   ├─ 6. forward ──── 转发到上游 LLM
   ├─ 7. extract ──── 一轮结束后异步回流 conversation + L0
   └─ 8. report ───── ClickHouse / Langfuse / Opik / Credit 上报

源码入口在 src/index.ts → server.ts，按协议分流到 handler.ts（OpenAI）、anthropicHandler.ts（Anthropic Messages）、codexHandler.ts（Responses）等。系统用户短路透传是第一阶段的重要出口：内部服务账号（如 Knowledge Service 用专用记账用户调 LLM）命中后跳过 session init 和注入，只做透明转发 + 计费——否则 Wiki 生成的请求也会被弹表单。

会话初始化：多客户端的状态机

sessionInit 要解决的问题是"把无状态的 HTTP 会话绑到 team/agent/task 三元组"，而难点在于每个客户端的交互能力不同。源码 src/session/ 下按客户端分子模块（claude-code/codebuddy/codex/dsh/workbuddy），各自实现一套适配：

  • Claude Code：借 CC 原生 AskUserQuestion 工具返回三连问；
  • CodeBuddy/WorkBuddy：各自的追问工具；
  • Codex：伪 function_call 表单（所以必须先切 Plan 模式，否则 agent 模式会自动执行掉）；
  • dsh：原生 ask_user_question tool call，渲染为 Web UI 按钮；CLI headless 自动 bypass；
  • Hermes/OpenClaw：不交互——x-team-id/x-agent-id/x-task-id/x-conversation-id 四 header 齐全时直接注册，缺了才尝试表单并最终 bypass。

状态存储在 ProxyStorage 中，key 按 {spaceId}/{userId}/{agentSource}/{sessionId} 组织。headerAutoSelect.onMismatch: "form" 等配置控制 header 与已有状态冲突时的行为。可选的 sessionInit.defaultTaskId 能在每个 team 的 Task 列表头部插入虚拟项"本次不关联任务"，解决"没建过 Task 卡流程"的问题。

注入管线：内容块与缓存哲学

注入器（src/injection/injectors/）产出这些 system prompt 块：

块来源内容
<tdai_profile_memory>Core L2/L3Agent Profile 场景块 + Team/Global 记忆
<cloud_skills>Core Skill RAG与当前问题相关的 Skill 摘要
<skill_tools>Skill Bridge如何通过 curl 调用 Skill 工具的说明
<knowledge_tools>KS绑定的 Wiki/CodeGraph 两步自发现协议
<session_context>session 状态本次绑定的 agent/task 信息
<asset_reflection>（可选）/analyse marker 开启时的复盘指令

而 L0/L1 刻意不内联注入——它们通过 <tdai_memory_tools> 以只读工具形式暴露给模型主动查询。原因在前文反复出现：L0/L1 每轮变化，内联会击穿上游 KV cache；L2/L3 和工具说明相对静态，可以稳定占据 system prompt 尾部命中缓存。多节点部署时还必须配置 injection.externalGatewayUrl 并统一用 COS 后端，否则各实例缓存不一致同样导致 cache miss。

失败哲学：任何注入器失败都非致命——回退原始 body 继续转发，绝不让记忆系统的故障变成用户对话的故障。上报同理（三路可观测互相独立、error-silent），限流则 fail-open。

存储抽象与降级链

src/storage/ 实现了 ProxyStorage 统一抽象，承载三类状态（inj:* 注入缓存、sk:* Skill 状态、vpin:* 版本 pin）。Key 布局：

proxy_cache/{ttl|nottl}/{spaceId}/{userId}/{agentSource}/{sessionId}/...

ttl/ 只放热缓存（可重建），nottl/ 放 binding 等必须持久化的业务态。四种后端的选型：

后端场景
cos生产多实例部署（跨节点共享，仅 kernel-sts 凭证）
sqlite单实例本地开发/CI（内置 sweeper 定期清 ttl 桶）
fs离线/docker 兜底（交给外部 tmpwatch）
memory测试兜底（重启即失）

降级链 cos → sqlite → fs → memory，任一 init 失败自动降级；/health 暴露 storage.effective 作为观测锚点。

限流与计费

  • Input TPM/QPM：按 spaceId × 最终模型 在 Redis 上做 60 秒滑动窗口；GET/PUT/DELETE /v3/admin/rate-limits 动态调整；
  • Credit 计费：上游响应完成后按定价表（pricing.ts）计算 CreditDelta 上报计费服务，仅识别路径带 /proxy/<spaceId>/ 的请求；
  • 用量明细：JSONL 结构化日志 + ClickHouse 按 turn 记录 token 明细。

其他值得知道的机制

  • mem: 指令拦截：见专章；
  • Skill/Memory Bridge：/skill-bridge/** 与 /memory-bridge/** 反向代理 Core 的 HTTP 工具，转发时注入 serviceToken——避免凭据出现在 LLM 可见的 prompt 里；
  • 按 agent name 的上游覆盖：upstream.agents 允许特定客户端走不同的上游（例如 claude-code 单独走 CCR）；
  • gateway/ 一致性哈希网关：可选的多实例负载均衡层，按 keyId 做一致性哈希保证同一用户落在同一 proxy 实例（配合 COS 后端）；
  • /analyse marker：URL 带 /analyse/ 段时（双闸门：配置 injection.assetReflection.markerOptIn=true 且 URL 显式携带），system prompt 末尾追加资产反思块，让 LLM 在回答末尾逐工具自评"这次注入值不值"。定位是效果评估，不建议对线上流量默认打开。

mem: 会话指令

mem: 指令是 Proxy 提供的最轻量的记忆操作入口：在对话里直接输入 mem: 开头的指令，Proxy 会拦截并就地处理——不用离开当前会话去开面板，也不用记 API。

现有指令

随 v2.0.0 发布，当前共三个：

指令说明
mem:sync刷新本次会话的全部资产注入（Skill / 记忆 / Knowledge / Task & Agent 描述）
mem:create-skill [提示词]把本次对话归档为 Skill，后台异步提取
mem:help显示指令帮助

格式约定：mem:<command>，冒号后不加空格，命令名大小写不敏感。

典型使用场景

mem:sync —— 你刚在面板上给当前 Agent 新绑了一个 Wiki 或改了 system prompt，但会话已经开了很久。输入 mem:sync，Proxy 重新拉取全部资产并刷新注入内容，无需重开会话。

mem:create-skill —— 刚和 agent 一起搞定了一次复杂的线上排障。输入 mem:create-skill，对话被归档进 Skill 抽取缓冲区，后台 LLM 异步提炼出带版本、步骤和验证规则的候选 Skill；稍后在面板审核发布。可选提示词可以引导抽取重点。

mem:help —— 除了查看用法，它还有一个隐藏价值：验证注入链路是否正常。如果 mem:help 没有响应，说明请求根本没经过 Proxy 的指令拦截层——通常是 base URL 配错或 session 未初始化。

实现机制

拦截发生在 Proxy 的请求预处理阶段（源码 src/mem-command/）：检测到用户消息以 mem: 开头时，Proxy 不把该消息转发给上游 LLM，而是就地生成响应返回。这意味着：

  • 指令消耗零 token；
  • 响应速度与上游模型无关；
  • 对客户端完全透明——任何走 Proxy 的客户端都能用，无论 CC、CodeBuddy 还是 Codex。

session init 完成是使用指令的前提：未绑定 team/agent/task 的会话中，涉及资产的指令没有作用对象。

路线图上的扩展

v2.0.1 计划把指令能力扩展到 Task 维度：

  • 在对话里直接创建 Task、更新 Task；
  • Task 与记忆资产的关联在会话内即时生效。

动机很实际："Task 是记忆归属的组织方式。能在对话里就地维护它，才不会出现『事情做完了，Task 还停在三天前的描述』。"

官方同时明确表示：接下来做哪些指令取决于真实使用中的需求——你在实际场景里反复需要什么操作（查看当前注入了什么？临时禁用某个资产？把某段对话存成记忆？），欢迎到 Issues 描述使用场景（比接口设计更有价值）。

MemoryKnowledge 内幕：Wiki 引擎与 CodeGraph

Knowledge Service（KS）负责把"文档和代码"变成 Agent 可用的记忆。它基于 Hono，默认端口 8421，API 前缀 /v3。

Wiki 引擎：ingest 流水线

一次 Wiki ingest 的完整旅程：

上传/拉取文档 ──► realWikiWorker ──► LLM 逐页抽取结构化页面
                                        │
                          mergePage 合并去重（单页失败不影响其他页）
                                        ▼
              每 wiki 独立的 index.db（FTS5 全文 + 链接图谱）

几个关键实现细节：

  • 每 wiki 独立 index.db：不是一个大库。读取走 LRU 池复用连接，写入用独立事务连接——单个 wiki 的构建不会拖累其他 wiki 的查询。
  • mergePage：新抽取的页面与已有页面做 LLM 辅助合并决策（更新、新建或跳过），重复 ingest 同一批文档不会产生重复页面。
  • run_id 代际机制：每次 ingest 有唯一 run_id，进度回调和终态回调都携带它——Panel 用它拒绝 clear 操作之后的迟到包，避免旧任务的进度污染新状态。
  • 自动摘要：构建完成时生成 wiki 摘要（LLM 生成）随终态回调返回，Panel 直接展示。

CodeGraph：代码的图索引

git clone ──► CodeGraph 索引（符号/文件树/调用关系）──► 探索查询

KS 通过 bridge 调用 CodeGraph 引擎（该项目复用了开源项目 colbymchenry/codegraph 的实现）。对外暴露八类查询：

code_search / explore / callers / callees / impact / node / status / files

其中 impact 是最有价值的一个：改代码前先查影响路径，这是文本检索永远给不了的能力。

Auto-Sync 调度器

可选功能（KNOWLEDGE_AUTO_SYNC_ENABLED=true 显式开启），实现在 src/store/auto-sync-scheduler.ts：

  • FIFO 内存队列 + 定长常驻 worker pool；worker 数 KNOWLEDGE_AUTO_SYNC_MAX_CONCURRENT 默认 3（clamp 1–20），扫描周期默认 10 分钟（clamp 1–60）；
  • 启动后延迟 30 秒首扫（让启动恢复流程先完成，避免抢磁盘）；
  • 只扫 status=ready 的 code-graph；inFlight Set 去重防重复入队；
  • worker 循环取队列执行同步，异常一律吞掉保证不死；同步中的仓库再次入队会得到 busy（对应 HTTP 409）。

Tools 协议：Agent 如何发现并调用知识

KS 的核心创新点之一是把知识查询做成自发现协议：

POST /v3/tools/list   → 返回可用工具清单（名称/描述/参数 schema）
POST /v3/tools/call   → 执行具体工具调用

Proxy 把这个协议渲染进 <knowledge_tools> 注入块：模型先 list 发现自己有哪些知识工具，再按需 call 读取相关页面、源码或影响路径。这就是"知识不整库注入，而是按需调用"的落地形态——平时知识只是可用的工具，真正需要时才进入上下文。

llm_binding：谁为 Wiki 生成的 token 买单

Wiki 抽取要烧 LLM token，这笔账必须算清楚。KS 用一张小表（store/llm-binding-store.ts）按 service_id 记录 LLM 绑定：

绑定状态生效配置
proxy 且配置齐全{proxy_base_url}/proxy/{service_id}/v1 —— 走 Proxy 以专用 knowledge-service 记账用户计费
byo 且配置齐全用户自带 OpenAI 兼容端点直连
无绑定/缺参由全局 LLM_MODE 决定；proxy 模式下刻意抛错而非静默直连

最后一条是刻意的工程决策：宁可启动失败也不静默兜底，强制 proxy 绑定链路被真正验证而不是掩盖 bug。另一个细节：binding 只覆写 endpoint/key，model 永远来自全局 LLM_MODEL——单一真相源，不存 per-instance model。

控制面接口在 /v3/internal/llm-binding/*（set/status/list），幂等 upsert——重发即覆写，这就是 Panel 启动时推送绑定的重绑机制。永不回显 api_key。

与 Panel 的回调协作

ingest_progress（流式）──► Panel /api/v1/knowledge/status-callback
status ready/failed（终态）──► 同上（含 auto summary + sync_error + run_id）

进度回调 fire-and-forget 且节流；终态失败重试 1 次（间隔 1s，5s 超时）后放弃，绝不阻塞主任务；TMC_CALLBACK_URL 为空则整体 no-op。Panel 收到 ready 后写内核资产明细并以 stash 的 owner 身份登记 meta_asset。

MCP stdio 通道

对支持 MCP 的宿主，KS 提供等价的 stdio 入口（bin/mcp.mjs → dist/mcp/server.js）。它是纯协议翻译层：ListTools 返回静态注册的 12 个工具（code-graph 8 个 + wiki 4 个），CallTool 按工具声明的 endpoint POST 回本机 HTTP API。管理操作刻意不暴露为 MCP 工具。

可选埋点

  • Langfuse：配 LANGFUSE_PUBLIC_KEY/SECRET_KEY 后上报 Wiki LLM 调用 trace；未配置时整体关闭。

MemoryPanel 内幕：管控面架构

Panel 的自我定位非常克制：无状态的控制台——不保存服务端登录会话、不维护本地用户库，业务数据全部由外部服务持久化。它做的只有三件事：校验调用方凭证并转发授权请求、聚合多源元数据、管理资产分配与绑定。

六边形架构：kernel 端口与适配器

后端按六边形（端口-适配器）组织，src/panel/ 下：

  ports/     KernelHttpPort · MetaKernelPort · SkillKernelPort · KnowledgeClientPort
  adapters/  fetch-* 实现：组装凭证头、日志脱敏、超时映射

FetchKernelHttpAdapter 是理解 Panel 行为的关键：

  • 组装 Authorization: Bearer <api_key> + x-tdai-service-id + 可选 x-tdai-user-key + x-request-id；
  • 日志脱敏：password/api_key/token/user_key 等敏感字段打码，字段截断 300 字符、JSON 截断 1200 字符；
  • AbortController 超时 15s，超时映射 504、网络错映射 502，统一包装为 KERNEL_TIMEOUT/KERNEL_UNAVAILABLE 信封。

凭证上下文每次请求由中间件从 Header + 注册表拼出 MetaCallContext。Panel 自己不做权限判定，而是把 caller 的 user_key 原样透传给内核——内核才是权威的权限裁判。

角色模型的实现细节

前端判定逻辑集中在 web/src/services/permissions.ts 与 backendStore.ts：

  • System Admin 看 auth/verify 返回的 user.user_type === 'system_admin'，是全局角色；
  • Team 内角色查 roleInTeam()——即 members 表记录的 admin | member | reviewer；
  • 判定顺序铁律：先判全局 admin 再查成员表；team owner 若不在 members 数组里按 member 兜底而非 admin（因为 UI 里 admin 语义是全局 admin，会被资源锁锁住页面）；
  • canManageAsset：admin 无全局资源特权，只能操作自己 owner 的资产；team admin 管本 team 资产。

后端侧 Panel 不自行判角色——一切 owner/ACL 校验由内核完成，Panel 只是忠实透传并展示内核的裁决。

隔离模型：withIsolation

v3 客户端的灵魂是三元组隔离。构造时缺任一维度直接抛 ParamError；需要跨作用域操作时用派生克隆：

const scoped = client.withIsolation({ sessionId: "sess-2", agentId: "agt-other" });

几条刻意的安全设计值得注意：

  • 写路径强制 session_id（缺失即抛错），读路径可省略以跨会话聚合；
  • deleteConversation 故意不回退默认 session——防止误删整个会话的数据；
  • 删除入参在客户端先归一化去重并限流（单批 ≤100，总 ≤5000）。

编写自定义 Adapter

如果你的 Agent 框架既不被 Proxy 支持、也不适合直接用 SDK 硬编码，就需要写一个 Adapter。官方的两个插件——OpenClaw 插件（TypeScript）与 Hermes 插件（Python）——就是为此而生的参考实现。

Adapter 三步曲

一个最小可用的 Adapter 只需要完成三件事：

  1. 会话捕获（capture）：会话结束或每轮完成后，把对话写入 L0；
  2. 记忆召回（recall）：构造 Prompt 前，召回 L1/L2/L3 并以有边界、可识别的方式注入上下文；
  3. 工具暴露（tools，可选但推荐）：把记忆搜索暴露为模型可主动调用的工具。

外加一条架构纪律：Adapter 保持无状态——不在插件进程内起 Gateway 子进程、不实现抽取逻辑；服务端是 L0 的权威存储，一切提炼交给 MemoryCore 的后台管线。

参考实现一：OpenClaw 插件

目录 MemoryCore/openclaw-plugin/，插件 ID memory-tencentdb-client，基于 npm TS SDK 构建。

捕获（src/hooks/capture.ts）：挂 agent_end 钩子，提取本轮 user/assistant 消息。工程细节值得借鉴：用 position slice + timestamp cursor 做去重（防止钩子重复触发导致重复写入）、还原被框架污染的原始 prompt、sanitizeText/stripCodeBlocks 过滤噪音后再写 L0。

召回（src/hooks/recall.ts）：挂 before_prompt_build 钩子，执行 searchAtomic + readCore（可选加 listScenarios 场景导航），格式化后注入带标签的简洁记忆上下文。recall.maxResults/includePersona/includeSceneNav 可配。

工具（src/tools/）三个：

  • tdai_memory_search：L1 原子记忆搜索；
  • tdai_conversation_search：L0 对话搜索；
  • tdai_read_cos：经 COS STS 直读 Pipeline 产物（persona.md / scene_blocks/*.md）。

安装：仓库根目录跑 bash MemoryCore/scripts/install-openclaw-plugin.sh。连接参数三件套：

TDAI_MEMORY_ENDPOINT=http://127.0.0.1:8420
TDAI_MEMORY_API_KEY=<与 Gateway 相同的 API Key>
TDAI_MEMORY_INSTANCE_ID=default

参考实现二：Hermes 插件

目录 MemoryCore/hermes-plugin/memory/memory_tencentdb/，同一模式的 Python 映射，额外多一层生产级可靠性设计，值得所有 sidecar 型集成学习：

  • Gateway Supervisor（supervisor.py）：自动发现并以子进程拉起 Node Gateway sidecar，轮询 /health 确认就绪；
  • 生命周期映射：prefetch(query) → POST /recall 同步注入 <memory-context>；sync_turn(user, assistant) → POST /capture 后台 daemon 线程 fire-and-forget（最多 4 并发背压）；shutdown/on_session_end → POST /session/end；
  • 熔断器：连续 5 次失败暂停 60s，避免记忆服务故障拖垮主 agent；
  • 诊断：sidecar stderr tail 保留用于排障。

暴露两个 LLM 工具：memory_tencentdb_memory_search 与 memory_tencentdb_conversation_search。

检查清单

交付自定义 Adapter 前逐项确认：

  • 所有请求带 x-tdai-service-id（实例隔离）；
  • v3 数据面调用携带完整三元组 + session_id（写路径强制）；
  • 注入内容有明确边界标记（如 XML 标签），模型能区分"记忆"与"当前指令"；
  • 召回结果限量限长，不挤占工作上下文；
  • 记忆服务不可用时静默降级——主流程绝不因记忆故障中断；
  • 不在 Adapter 本地落对话数据（服务端是唯一权威存储）；
  • 凭证只从环境变量读取，不写入代码与配置仓库。

部署形态进阶：单机到多节点

入门篇的一键三件套适合体验与小团队。本章讨论当规模、可靠性或合规要求提高时，各组件如何演进。

形态一：Standalone 单机（默认）

MemoryCore 的 standalone 模式是整个项目的默认形态：

  • 状态全在进程内：任务队列用内存 Map + checkpoint 文件，定时器用 setTimeout；
  • 存储：SQLite + 本地数据目录（~/.memory-tencentdb/memory-tdai）；
  • 唯一外部依赖是 LLM API。

适用：个人使用、开发调试、Agent sidecar。局限：单点、无水平扩展、重启瞬间丢失进行中的管线任务（checkpoint 会恢复大部分状态）。

形态二：Service 模式

把 deployMode 切到 service 后，有状态的部分全部外置：

组件外置为
任务队列Redis Stream
定时调度16 分片的 Timer ZSET（Lua 脚本原子认领）
并发控制分布式锁 pipeline:{inst:tid:aid}[:s:sess]
向量存储TCVDB（服务端原生 hybrid 检索）
大对象COS
元数据MongoDB（可选）

关键在于业务 handler 与执行器完全复用——两态差异收敛在 pipeline-manager.ts 与 stateful-pipeline-manager.ts 的状态管理层。这意味着从单机迁到 service 不需要改任何业务代码，只改配置与基础设施。

Proxy 的多节点要点

Proxy 无状态化的前提是三个配置同时到位，缺一不可：

  1. storage.backend=cos：会话/注入/Skill 状态跨节点共享。降级链上 sqlite/fs/memory 都不能多实例共享——用它们做多节点会导致各实例状态分裂；
  2. injection.externalGatewayUrl 显式配置：让注入缓存指向统一入口。否则每个实例各自缓存，同一会话的请求轮转在不同实例上会造成上游 KV cache 反复 miss——成本和延迟双输；
  3. 可选的一致性哈希网关（MemoryProxy/gateway/）：按 keyId 一致性哈希把同一用户固定到同一 proxy 实例，进一步稳定缓存命中。/skill-bridge 与 /memory-bridge 前缀由外层 gateway 原样透传到 proxy 实例。

运维配套：/v3/instance/proxy-destroy 在实例销毁时清 COS 缓存；/health 的 storage.effective 是确认实际生效后端的观测锚点；停机前确保 L0 pending write 队列 flush 完成。

合并镜像与镜像发布

panel-knowledge-combined：Panel + KS 打进一个镜像（deploy/panel-knowledge-combined/），四阶段构建（panel-ui-builder → panel-builder → knowledge-builder → runtime）。入口脚本 start-combined.sh 优先尊重用户 bind-mount 的 metadata-instances.json；没有时用 env 现场生成单实例注册表，然后同容器拉起双进程。云上部署最少只需三项配置：instances JSON、KNOWLEDGE_PUBLIC_BASE_URL（必须含 /v3 且外部可达）、KNOWLEDGE_LLM_PROXY_BASE_URL。

dockerhub 发布流水线（deploy/dockerhub/publish.sh）：

VERSION=x.y.z ./publish.sh all   # 或 memory-core / memory-proxy / memory-hub

buildx 多架构（linux/amd64 + arm64）；NAMESPACE=agentmemory；支持 ALSO_LATEST/PUSH/DRY_RUN/APT_MIRROR 等开关。两个值得知道的细节：Proxy 的私有模块 cost-guard 用 stub 包顶替（运行时动态 import 失败自动降级直通）；MemoryCore 的 integrations 目录在 .dockerignore 中排除并走 fallback——开源镜像不携带内部集成代码，但功能完整。

安全加固清单

生产部署前过一遍：

  • Gateway 层：非回环监听必须设置 TDAI_GATEWAY_API_KEY；CORS 默认关闭，只放行明确可信 Origin，禁止 *；
  • Proxy 层：启用 auth.enabled=true；env 注入 TDAI_PROXY_ADMIN_API_KEY 保护运维端点；
  • 凭证管理：一切 Secret 走环境变量或 Secret Manager；.env/数据库文件/日志/导出数据绝不入库；提交前跑 bash MemoryPanel/scripts/secret-scan.sh --strict；
  • 租户隔离：每个请求校验实例与 Team/User/Agent 归属，防止跨租户访问；
  • 凭证泄漏应急：凭证一旦进入 Git 历史，立即轮换并清理历史。

容量与成本直觉

最后给几条 sizing 直觉：

  • 记忆提炼（L1/L2/L3）的 LLM 开销与对话量成正比，everyNConversations 调大可省 token 但记忆更新变慢；
  • Wiki ingest 是一次性大消耗（整批文档抽取），之后增量维护很便宜；
  • Proxy 注入本身零 LLM 成本，但注入内容增加会推高每轮 input token——给不同角色配不同 Loadout 同时也是成本控制手段；
  • CodeGraph 索引构建 CPU 密集，Auto-Sync 的扫描周期与并发数按仓库数量与机器规格权衡。

可观测性体系

记忆系统是异步的、多级的、跨四个服务的——出了问题"为什么这条记忆没生成/没被注入"必须靠可观测性回答。本章梳理三套互相独立的上报体系与日志约定。

Proxy 的三路 APM 上报

每次经过 Proxy 的 turn 可以同时上报三个平台，三路完全独立，任一失败不影响业务与其他路：

平台粒度内容
OpiktraceLLM 调用链路追踪
Langfusetrace（一个 trace = 一个 turn）对话轮次级追踪
ClickHouse按 turntoken 用量明细（计费数据源）

源码对应 src/opik.ts / langfuse.ts / clickhouse.ts。设计哲学是 error-silent：上报失败记日志、吞异常，绝不把可观测性故障传染给用户对话。

KS 的埋点

Knowledge Service 有两套可选遥测：

ClickHouse 工具调用日志：KNOWLEDGE_CLICKHOUSE_ENABLED=true 后，每个 POST /v3/tools/call 写入 tool_call_logs 表。隐私处理值得细看：请求正文递归脱敏并截断到 512 bytes；若调用方传了 x-conversation-id、x-tdai-user-id/team-id/agent-id/space-id/turn-seq 等 header，这些维度一并入库用于归因——但密钥永远不进库。

Langfuse：配置 LANGFUSE_PUBLIC_KEY + LANGFUSE_SECRET_KEY 后上报 Wiki 生成过程的 LLM 调用；未配置时整体关闭，零开销。

Core 的内置度量

MemoryCore 不依赖外部 APM 也有一层自观测：

  • GET /health：除了存活探针，还暴露 pipelineWorker 的 tasksConsumed/tasksCompleted 计数——这是确认"提炼管线在干活"最直接的指标；
  • 召回度量（src/core/report/metric-tracking-recall.ts）：记录召回最高分（recall_top_score）等指标；
  • 性能日志标签：如 [skill-perf] 输出 Skill 检索耗时分解。

标签来源

效果评估：注入到底值不值

除了"系统是否正常"，还有一类问题更难答："注入的记忆/Skill/知识对回答质量有没有实际帮助？"Proxy 为此内置了资产反思机制（asset reflection）：

  • 双闸门开启：config 里 injection.assetReflection.markerOptIn: true 且 URL 显式带 /analyse/ 段： 
    http://<proxy>:8096/claude-code/<spaceId>/analyse/v1/messages
  • 开启后 system prompt 末尾追加 <asset_reflection> 块，指导 LLM 在最终回答末尾只对本轮真正调用过的资产工具逐个复盘：是否起作用、拿到了什么关键信息、或为何未命中；
  • 本轮完全没用工具也要输出固定一行："【资产反思】本轮未使用任何云端资产工具。"

定位是接入效果验证：把评测集或 staging 会话导到 /analyse URL 上，直接读回 LLM 自己给出的逐工具评价。markerOptIn=false 时带 marker 的请求直接 404——刻意防止客户端以为开了实际却 fall through。不要对线上真实流量默认打开。

建议的最小监控组合

生产环境至少盯四样东西：

  1. 四个服务的 /health（Core 的 pipelineWorker 计数尤其重要）；
  2. Proxy /health 里的 storage.effective——确认存储后端没有意外降级到 memory；
  3. ClickHouse 的 token 消耗趋势（成本异常往往先在这里显形）;
  4. 定期抽查 Generation Log——记忆质量回归比服务故障更隐蔽。

升级操作建议

  • Docker 部署：named volume 里的数据跨版本保留；拉新镜像重启即可。跨大版本（v1→v2）先对 volume 里的数据目录跑迁移脚本；
  • 源码部署：pull 后 npm install && npm run build 再迁移再启动；
  • SDK：注意 npm 包名曾迁出 -v2 后缀的历史；Python 包根导入默认给 v2 兼容客户端，v3 要显式 from tencentdb_agent_memory.v3 import ...；
  • Proxy 客户端配置：小版本内兼容；大版本留意 INSTALL 文档中的已知限制变化（例如 x-task-id 必填是否放开）。

CI 红线：贡献者必读

项目的 CI（.github/workflows/pr-ci.yml）目前聚焦 MemoryCore，五个 job：

  1. Install：Node 22 + 依赖缓存；
  2. Pack：npm pack 并上传 tgz 工件（7 天留存）;
  3. Manifest：校验 openclaw.plugin.json 合法性与 package.json 的 OpenClaw 扩展元数据；

    • 禁止触碰记忆模块红线文件（state/pipeline-worker/integrations/redis）;
    • 禁止 src/core/skill/** 新增直接 fs import。

这条红线的背景：Skill 抽取队列被刻意设计为与记忆管线隔离的独立队列——保证 Skill 归档的延迟不影响主记忆链路，也保证它不依赖进程本地状态。改动这些区域前先读对应设计文档。

术语表

按概念相关性分组，供阅读文档与源码时快速对照。

记忆模型

L0 Conversation：原始对话层。完整保留上下文，用于核对原话、时间与来源。

L1 Atom（原子记忆）：从对话中提取的事实、偏好、约束与事件，是最常被精确召回的一层。

L2 Scenario / Profile（场景记忆）：围绕项目或场景组织的知识块（Scene Markdown），挂在 Agent Profile 下，用于快速恢复工作场景。

L3 Core / Persona（核心画像）：跨场景沉淀的长期画像与稳定模式。

Generation Log（生成溯源）：每次 L1/L2/L3 生成留下的证据记录——Prompt ID、版本、内容哈希、输入输出引用。

资产与权限

Memory Asset（记忆资产）：Chat Memory、Skill、Wiki、CodeGraph 的统一登记形态，携带 Owner/Team/可见性/版本等元信息。

Visibility（可见性）：private（仅 Owner）/ team（团队成员）/ restricted（ACL 精确授权）/ agent（定向装配）四级。

Fixed Binding（固定绑定）：Agent 与资产间的显式绑定关系，Loadout 的数据基础。

ACL：User/Role/Agent 粒度的访问控制表，配合 restricted 可见性使用。

Loadout（装配）：一个 Agent 实际携带的记忆资产组合——先按权限收敛、再按问题召回。

组织结构

Team / Agent / Task 三元组：v3 数据面的强隔离维度。Team 是资产容器；Agent 是角色化执行者（也是被管理的元数据实体）；Task 是可选的工作抓手。

Memory Instance（记忆实例）：逻辑隔离的数据单元，请求经 x-tdai-service-id 声明；在 Proxy URL 中表现为 <spaceId> 段。

System Admin / Team Admin / Member：全局运维角色与团队内角色的两层体系。

服务与接口

MemoryCore：记忆与元数据核心服务（:8420），数据权威所在。

Knowledge Service（KS）：Wiki + CodeGraph 引擎（:8421/:8424），API 前缀 /v3。

Panel / Memory Hub：无状态 Web 管理控制台（:8125）。

MemoryProxy：透明 LLM 请求代理（:8096），在转发前后完成会话初始化、注入、回流与上报。

Session Init（会话初始化）：首次对话时绑定 team → agent → task 的交互流程；无法交互的客户端用 x-team-id 等 header 直接注册。

Tools 协议：POST /v3/tools/list + /v3/tools/call 的能力自发现协议，知识按需调用的落地形态。

存储与算法

RRF（Reciprocal Rank Fusion）：多路检索结果的排名融合算法，score = Σ 1/(k + rank)，k=60。

BM25 / FTS5：关键词检索算法与其 SQLite 实现；配合 jieba 中文分词。

sqlite-vec / TCVDB：本地向量扩展与腾讯云向量数据库；后者提供服务端原生 hybrid 检索。

ProxyStorage：Proxy 的统一存储抽象，四后端 cos/sqlite/fs/memory 加降级链。

Offload：大对象到 COS 或本地文件的下沉存储。

运行机制

Pipeline（提炼管线）：L0 → L1 → L2/L3 的异步生成系统，由 Scanner 触发、Worker 执行。

Warm-up（预热阈值）：新会话的触发阈值 1→2→4→8→…→N 翻倍爬升机制，保证冷启动快速产出首批记忆。

KV Cache 保护："稳定内容进 system prompt 尾部命中缓存，易变内容走工具"的注入分层原则。

mem: 指令：Proxy 在对话内拦截的轻量操作入口，如 mem:sync、mem:create-skill。

Adapter 三步曲：自定义接入件的标准模式——capture（写 L0）、recall（召回注入）、tools（暴露查询工具）。

FAQ 汇编

按主题归档的常见问题。部署类问题另见常见问题排查。

产品与定位

Q：和直接给 Agent 加一个"记忆插件"有什么区别？

单机记忆插件把记忆锁在单个 Agent/框架里。本项目的记忆是资产化的团队资源：带 Owner、版本、可见性与 ACL，可以跨框架迁移、跨成员共享，由人审核与装配。Proxy 模式下甚至不需要任何插件——改一个 base URL 就接入。

Q：必须用腾讯云的产品吗？

不需要。默认形态只用 SQLite + 本地文件 + 任一 OpenAI-compatible LLM API；TCVDB（腾讯云向量库）与 COS 都是可选升级项，用于规模化场景。

Q：支持哪些 Agent？

经 Proxy 零代码接入：Claude Code、CodeBuddy、WorkBuddy、Codex CLI、DeepSeek Harness、Hermes、OpenClaw；任何 OpenAI 兼容平台可走通用接入法；自研运行时用 TS/Python SDK。

架构与数据

Q：我的对话数据存在哪里？

standalone 默认在 ~/.memory-tencentdb/memory-tdai（SQLite + 本地文件）。Docker 部署在 named volume 中。Proxy 自身不落任何记忆数据。

Q：L1/L2/L3 是实时生成的吗？

不是。写入 L0 后由后台管线异步提炼：默认每 5 轮触发一次（新会话有 1→2→4→8 的预热加速），会话空闲超时也会触发。这是刻意设计——提炼不该阻塞对话本身。

Q：记忆会不会把上下文撑爆？

不会，这是设计的核心关切之一：召回有条数上限、字符预算与超时三重护栏；注入侧遵循"稳定进缓存、易变走工具"的分层；知识（Wiki/CodeGraph）平时只是可调用的工具，不进入上下文。

Q：自动抽取的记忆错了怎么办？

当前版本可在面板删除后重建；v2.0.1 正式版计划开放 L1-L3 的面板编辑。自定义 Memory Prompt 可以从源头调整提炼关注点，减少系统性偏差。

使用技巧

Q：怎么让记忆更快"长出来"？

做真实工作对话（改文件、跑测试、给结论），明确说出约束与偏好；用 mem:create-skill 显式归档有价值的过程；导入历史 Session 补足存量。promptMode=code 只对代码类对话有效，闲聊抽不出东西。

Q：如何验证注入真的生效了？

三步：mem:help 有响应 → Core /health 的 pipelineWorker 计数增长 → 用 /analyse marker 做一轮资产反思评估（见可观测性章）。

Q：多个 Agent 可以共享同一条记忆吗？

可以，这正是 Team 的意义：把资产可见性设为 team 或通过 ACL 授权，再绑定到需要的 Agent。注意 Skill 的共享方式是 fork 副本而非绑定。
